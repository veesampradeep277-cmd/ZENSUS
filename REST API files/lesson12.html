API Validation & Error Handling

Learn how APIs validate incoming data, reject invalid requests, handle unexpected problems, return meaningful HTTP status codes, and build consistent JSON error responses.

01

What is API Validation?

Validation means checking whether incoming API data satisfies the rules required by the application before that data is processed or stored.

Simple Example

Suppose an API creates a student. The API expects:

  • A name
  • A valid email address
  • A positive age
  • A valid course

If the client sends invalid information, the API should not blindly save it.

Incoming Request 
POST /students/

{
    "name": "",
    "email": "hello",
    "age": -5,
    "course": ""
}

The server validates each field and returns useful information about the problems.

Validation Error 
HTTP/1.1 400 Bad Request

{
    "error": "Validation failed",
    "fields": {
        "name": "This field is required.",
        "email": "Enter a valid email address.",
        "age": "Age must be greater than 0.",
        "course": "This field is required."
    }
}
02

Why Validation Matters

🛡️

Protect Data

Prevents invalid or unexpected values from entering the database.

🎯

Maintain Data Quality

Ensures that stored information follows the application's rules.

🚫

Reject Bad Requests

The API can stop invalid operations before they reach business logic or database operations.

💬

Useful Feedback

Structured validation errors help frontend developers understand what needs to be corrected.

Important: Validation is not only a frontend responsibility. The backend/API must validate incoming data because clients cannot be trusted to enforce server-side rules.
03

Types of API Validation

Required Field

Checks whether required information was provided.

Data Type

Checks whether the value has the expected type.

Length

Checks minimum and maximum length.

Range

Checks whether numbers fall within an allowed range.

Format

Checks emails, dates, phone numbers and other structured values.

Business Rules

Checks application-specific rules that simple type validation cannot handle.

The API should verify that each field contains the expected type of data.

Validation rules should match the actual requirements of the application. Do not invent arbitrary restrictions that the business logic does not require.

Business Rule Validation

Business validation checks rules specific to the application's real-world requirements.

Example — Course Registration

Suppose a student wants to enroll in a course. The API may need to check:

  • Does the student exist?
  • Is the course available?
  • Has the student already enrolled?
  • Has the course reached its maximum capacity?
  • Does the student satisfy prerequisites?
Concept

Important difference:

"Age must be an integer" is a data validation rule.

"Student must be at least 18 to register for this course" is a business rule.

Nested Data Validation

REST APIs sometimes receive nested JSON objects or arrays. Each level may require validation.

Nested Request 
{
    "student": {
        "name": "Pradeep",
        "email": "pradeep@example.com"
    },
    "course": {
        "name": "REST API",
        "duration": 30
    }
}

The API may validate both the student object and the course object.

Nested Validation Error 
{
    "error": "Validation failed",
    "fields": {
        "student.email": "Enter a valid email address.",
        "course.duration": "Duration must be greater than 0."
    }
}

What is API Error Handling?

Error handling is the process of detecting problems, stopping the failed operation safely, and returning an appropriate response to the client.

Request
→
Process
→
Error?
→
Handle
→
Response

Types of Problems

400

Invalid Request

The client sent data that the API cannot accept.

401

Authentication Error

The request lacks valid authentication credentials.

403

Permission Error

The requester is authenticated but lacks required permission.

404

Resource Not Found

The requested resource does not exist.

409

Conflict

The request conflicts with the current state of a resource.

500

Server Error

The server encountered an unexpected problem.

11

Choosing the Correct HTTP Status Code

Status Meaning Typical API Situation
400 Bad Request Malformed or invalid request data
401 Unauthorized Authentication is missing or invalid
403 Forbidden Authenticated requester lacks permission
404 Not Found Requested resource does not exist
405 Method Not Allowed HTTP method is not supported for endpoint
409 Conflict Request conflicts with current resource state
422 Unprocessable Content Request syntax is valid but semantic validation fails
429 Too Many Requests Rate limit exceeded
500 Internal Server Error Unexpected server-side failure
503 Service Unavailable Service temporarily unable to handle request
400 vs 422: Different API designs use these codes differently. The important point is to define a consistent convention for your API and apply it consistently.

Structured Error Responses

A good API should return predictable error responses instead of random messages.

Simple Error

JSON 
{
    "error": "Student not found"
}

Detailed Error

JSON 
{
    "success": false,
    "error": {
        "code": "STUDENT_NOT_FOUND",
        "message": "Student with ID 101 was not found."
    }
}

Validation Error

JSON 
{
    "success": false,
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "One or more fields are invalid.",
        "fields": {
            "name": "This field is required.",
            "email": "Enter a valid email address.",
            "age": "Age must be greater than 0."
        }
    }
}
Why structured errors are useful:

Frontend applications can inspect the error code and individual fields instead of trying to understand an unpredictable text message.
13

Exception Handling

Sometimes an API encounters an unexpected runtime problem. Backend applications should handle expected failures and avoid exposing internal implementation details to clients.

Python Example

Python 
def get_student(student_id):

    try:
        student = find_student(student_id)

        return {
            "id": student.id,
            "name": student.name
        }

    except StudentNotFoundError:
        return {
            "error": "Student not found"
        }

    except Exception:
        return {
            "error": "Internal server error"
        }
In a real API, exception handling should also return the correct HTTP status code. The exact implementation depends on the backend framework.

Expected vs Unexpected Errors

Type Example Handling
Expected Student does not exist Return controlled 404 response
Expected Invalid input Return validation error
Expected Not authorized Return 401/403
Unexpected Unhandled server failure Log internally and return safe 5xx response

Safe Error Messages

Error messages should help clients understand what happened without revealing sensitive internal information.

Bad Example

Do Not Expose Internal Details 
{
    "error": "PostgreSQL connection failed at
    192.168.1.20 using password XYZ..."
}

Better Example

Safe API Response 
{
    "error": {
        "code": "INTERNAL_SERVER_ERROR",
        "message": "An unexpected error occurred."
    }
}
Do not expose:
  • Passwords
  • API secrets
  • Database credentials
  • Private keys
  • Internal stack traces
  • Unnecessary server paths
  • Sensitive infrastructure details

Internal Logging

The server can log detailed technical information internally while returning a safe message to the client.

Detailed Request Lifecycle

  1. Client sends an HTTP request.
  2. API parses the request body, headers and parameters.
  3. The API checks authentication when required.
  4. The API validates the input data.
  5. If validation fails, the API returns a structured 4xx response.
  6. If validation succeeds, business rules are checked.
  7. The API performs the required database or application operation.
  8. If an expected problem occurs, a controlled error response is returned.
  9. Unexpected failures are logged internally and handled safely.
  10. The API returns a consistent HTTP response to the client.

Lesson Takeaway

  • Validation checks whether incoming data follows the API's rules.
  • Validation should happen on the server, even if the frontend already validates the data.
  • Common validation types include required fields, data types, length, range, format and business rules.
  • Business validation checks application-specific rules.
  • API errors should have appropriate HTTP status codes.
  • 4xx responses generally indicate problems with the request, authentication, authorization or requested resource.
  • 5xx responses generally indicate server-side failures.
  • Structured JSON error responses make APIs easier for frontend applications to consume.
  • Expected failures should be handled deliberately instead of being treated as unexpected crashes.
  • Unexpected technical errors should be logged internally.
  • Do not expose passwords, secrets, stack traces or sensitive infrastructure details in API responses.
  • A consistent error format makes an API easier to test, debug and integrate.
