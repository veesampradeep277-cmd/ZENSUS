Building PUT, PATCH & DELETE APIs

Learn how APIs modify and remove resources using PUT, PATCH and DELETE. Understand full updates, partial updates, request bodies, path parameters, validation, status codes, idempotency, complete CRUD workflows and real API design.

01

PUT, PATCH & DELETE

In the previous lesson, you learned GET and POST. Now we complete the remaining major CRUD operations.

PUT

Replace / Update

PUT is commonly used when the client wants to replace the current representation of a resource with a new representation.

Example 
PUT /students/101/
PATCH

Partial Update

PATCH is commonly used when only part of an existing resource needs to be changed.

Example 
PATCH /students/101/
DELETE

Remove

DELETE is used to request removal of a resource.

Example 
DELETE /students/101/
Simple memory trick:

PUT → Replace / update the resource
PATCH → Change part of the resource
DELETE → Remove the resource
02

Building a PUT API

PUT is commonly used to replace an existing resource with a new representation.

Example Resource

Current Student 
{
    "id": 101,
    "name": "Pradeep",
    "email": "pradeep@example.com",
    "age": 21,
    "course": "Python"
}

Suppose the client wants to replace this student's information. The request can be:

PUT Request 
PUT /students/101/
Content-Type: application/json

{
    "name": "Pradeep Kumar",
    "email": "pradeep@example.com",
    "age": 22,
    "course": "Django"
}

What Happens?

1
Client identifies resource

The URL contains /students/101/.

2
Client sends replacement data

The request body contains the new representation.

3
Server validates the request

The API checks whether the submitted data is acceptable.

4
Server updates the resource

The existing representation is replaced according to the API's update rules.

5
Server returns a response

The response communicates whether the operation succeeded.

A PUT operation may also return 204 No Content when the server successfully processes the update but does not return a response body.

PUT and Required Fields

When an API defines PUT as a complete replacement operation, the client may be expected to provide all fields required for the resource representation.

Important:

The exact PUT behavior depends on the API contract. Always follow the documentation of the API you are using.

Building a PATCH API

PATCH is used for partial modifications. Instead of sending the complete resource, the client can send only the fields that need to change.

Current Student

Existing Resource 
{
    "id": 101,
    "name": "Pradeep",
    "email": "pradeep@example.com",
    "age": 21,
    "course": "Python"
}

Suppose only the course needs to change.

PATCH Request 
PATCH /students/101/
Content-Type: application/json

{
    "course": "Django"
}

The other fields can remain unchanged according to the API's defined behavior.

Result

Updated Resource 
{
    "id": 101,
    "name": "Pradeep",
    "email": "pradeep@example.com",
    "age": 21,
    "course": "Django"
}
Key idea:

PATCH is useful when you want to modify only selected properties without sending the entire resource representation.

DELETE Request Flow

1
Client chooses resource

The client identifies the resource using its URL.

2
Client sends DELETE

Example: DELETE /students/101/

3
Server checks the resource

The API determines whether student 101 exists and whether the client is allowed to perform the operation.

4
Resource is removed

The backend performs the deletion according to its data model and business rules.

5
Server returns status

The API reports the result, commonly with 204 on successful deletion.

Real-world caution:

Deleting data can be irreversible. Production applications may use soft deletion, backups, confirmation rules, audit logs, or permission checks depending on the application's requirements.
08

Path Parameters

PUT, PATCH and DELETE commonly operate on one specific resource. The resource identifier is therefore placed in the URL path.

Examples 
PUT    /students/101/
PATCH  /students/101/
DELETE /students/101/

In these examples, 101 is the resource identifier.

Collection vs Individual Resource

URL Meaning
/students/ The student collection
/students/101/ Student resource 101
/students/102/ Student resource 102
A common REST API design is to use the collection endpoint for creating resources with POST and the individual resource endpoint for modifying or deleting a specific resource.

Request Bodies for PUT & PATCH

PUT and PATCH commonly send JSON in the request body.

PUT Body

Complete Representation Example 
{
    "name": "Pradeep Kumar",
    "email": "pradeep@example.com",
    "age": 22,
    "course": "Django"
}

PATCH Body

Partial Update Example 
{
    "age": 22
}

Content-Type

Header 
Content-Type: application/json

This tells the server that the request body is JSON.

Remember:

The HTTP method tells the server the intended operation. The URL identifies the resource. The request body contains data when the operation requires it.

Idempotency — Important Concept

Idempotency is an important HTTP concept when learning PUT and DELETE.

An operation is idempotent when making the same request multiple times has the same intended effect on the resource state as making it once.

PUT Example

Request 1 
PUT /students/101/

{
    "name": "Pradeep",
    "course": "Django"
}

Sending the same intended PUT request again should result in the same target representation, assuming the API's state and request conditions are unchanged.

DELETE Example

DELETE 
DELETE /students/101/

Once student 101 has been deleted, sending the same request again does not normally delete another student. The resource remains absent.

Important distinction:

Idempotent does not necessarily mean that every repeated request returns the exact same response. It means the intended effect on the resource state is the same.

Common HTTP Method Property

Method Typical Idempotency
GET Yes
PUT Yes
PATCH Depends on the operation design
DELETE Yes
POST No, generally not

Common PUT, PATCH & DELETE Errors

1. Updating a Resource Without an ID

Usually Incorrect for an Individual Update 
PUT /students/

For an individual resource update, a common REST design is:

Individual Resource 
PUT /students/101/

2. Sending Invalid JSON

Invalid JSON 
{
    "name": "Rahul",
    "age": 22,
}

The trailing comma makes this invalid JSON.

3. Forgetting Content-Type

Header 
Content-Type: application/json

4. Updating a Resource That Does Not Exist

Request 
PATCH /students/9999/

{
    "course": "Django"
}

If the resource does not exist, the API should follow its documented behavior, commonly returning 404 Not Found.

5. Deleting Without Permission

A real application may require authentication and authorization before allowing a DELETE request.

Never assume that hiding a Delete button in the frontend is enough for security.

The backend must enforce authorization.

6. Confusing PUT and PATCH

PUT is generally associated with replacing a resource representation, while PATCH is specifically intended for partial modification.

Lesson Takeaway

  • PUT is generally used to replace or fully update a resource representation.
  • PATCH is designed for partial modification.
  • DELETE requests removal of a resource.
  • Individual resources are commonly identified using path parameters such as /students/101/.
  • PUT and PATCH commonly use JSON request bodies when data is being submitted.
  • A successful update can commonly return 200 OK or 204 No Content.
  • A successful DELETE can commonly return 204 No Content.
  • A missing resource commonly results in 404 Not Found.
  • Authentication and authorization should be enforced by the backend for protected operations.
  • PUT and DELETE are generally idempotent; PATCH depends on how the particular operation is designed.
  • Together with GET and POST, these methods complete the main HTTP operations used in CRUD-style APIs.
