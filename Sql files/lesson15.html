1. What Is a Transaction?

A transaction is a sequence of one or more database operations treated as a single logical unit of work.

Core idea: Either all required operations succeed, or the database can undo the incomplete work.

🏦 Real-World Example — Bank Transfer

Imagine transferring ₹1,000 from Account A to Account B.

  1. Subtract ₹1,000 from Account A.
  2. Add ₹1,000 to Account B.

What happens if step 1 succeeds but the system crashes before step 2?

Without proper transaction handling, money could disappear from Account A without reaching Account B.

A transaction ensures the two operations behave as one logical unit.

START Begin transaction
→
DEBIT Subtract money
→
CREDIT Add money
→
COMMIT Save changes

2. Basic Transaction Syntax

Common SQL systems provide statements for starting, committing and rolling back transactions. Exact syntax and default behavior can differ between database systems.

SQL 
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE account_id = 101;

UPDATE accounts
SET balance = balance + 1000
WHERE account_id = 202;

COMMIT;
If both updates succeed and the transaction is committed, the changes become durable according to the database's transaction and storage guarantees.

4. ACID Properties

ACID is the foundation of reliable database transactions.

A

Atomicity

The transaction behaves as an all-or-nothing unit.

C

Consistency

Transactions preserve defined database rules and constraints.

I

Isolation

Concurrent transactions are controlled so their intermediate effects are appropriately hidden according to the isolation level.

D

Durability

Committed changes survive failures according to the DBMS durability guarantees.

Atomicity

Suppose an order creation requires:

  1. Create order.
  2. Insert order items.
  3. Reduce inventory.
  4. Record payment.

If a required operation fails, the application may need the whole transaction rolled back.

Consistency

Consistency means a successful transaction takes the database from one valid state to another valid state according to constraints, data types, triggers and other enforced rules.

Isolation

Multiple transactions may run at the same time. Isolation controls what one transaction can observe from another transaction.

Durability

After a successful commit, the DBMS uses its recovery mechanisms, logging and storage system to make committed data survive failures.

5. COMMIT

COMMIT tells the database to successfully finish the current transaction and make its changes permanent according to the DBMS transaction semantics.

SQL 
START TRANSACTION;

UPDATE students
SET fees_paid = fees_paid + 5000
WHERE student_id = 101;

COMMIT;
After COMMIT, a normal ROLLBACK cannot simply undo that already committed transaction. A separate compensating transaction may be needed to reverse the business action.

6. ROLLBACK

ROLLBACK cancels the current transaction and undoes its uncommitted changes, subject to the DBMS's transaction semantics.

SQL 
START TRANSACTION;

UPDATE accounts
SET balance = balance - 5000
WHERE account_id = 101;

-- Something went wrong

ROLLBACK;
ROLLBACK is not the same as deleting data manually. It reverses changes belonging to the current uncommitted transaction.

7. SAVEPOINT

A SAVEPOINT creates a named point inside a transaction that you can roll back to without necessarily cancelling the entire transaction.

SQL 
START TRANSACTION;

INSERT INTO orders(order_id, customer_id)
VALUES (101, 1);

SAVEPOINT order_created;

INSERT INTO order_items(order_id, product_id, quantity)
VALUES (101, 55, 2);

-- Suppose the item operation needs to be undone

ROLLBACK TO SAVEPOINT order_created;

-- Continue with other work

COMMIT;

Important

SAVEPOINT behavior and syntax are widely available but details such as naming, nesting and release behavior can vary by DBMS.

10. Transaction Isolation

Imagine two users modifying or reading the same data at nearly the same time. The DBMS must control what each transaction can see.

Why Isolation Matters

Poorly controlled concurrency can produce anomalies such as:

Dirty Read

Transaction B reads data written by Transaction A before A commits. If A rolls back, B observed data that never became committed.

Non-Repeatable Read

A transaction reads the same row twice and gets different committed values because another transaction changed it.

Phantom Read

Repeating a range query can produce additional or missing rows because another transaction inserted or deleted matching rows.

11. Isolation Levels

SQL standards define isolation concepts, while exact implementation, MVCC behavior and anomaly guarantees can vary between database engines.

Isolation Level Dirty Read Non-Repeatable Read Phantom Read General Idea
Read Uncommitted Possible Possible Possible Weakest isolation
Read Committed Prevented Possible Possible Only committed data is read
Repeatable Read Prevented Generally prevented DB-specific Stronger repeatability
Serializable Prevented Prevented Prevented Strongest standard isolation
Do not memorize the table as a promise that every DBMS implements every level identically. PostgreSQL, MySQL/InnoDB, SQL Server and Oracle use different concurrency mechanisms and may expose different behavior.

12. MVCC — Multi-Version Concurrency Control

Many modern databases use some form of MVCC to allow readers and writers to work concurrently using multiple row versions or equivalent mechanisms.

Transaction A Reads version 1
→
Transaction B Creates new version
→
Commit New version visible according to isolation

MVCC is one reason database concurrency can be more sophisticated than simply “locking every row.”

13. Locks

Databases use locking and/or version-based techniques to coordinate concurrent access.

🔓 Shared Lock

Conceptually allows compatible reads while protecting data from conflicting modifications.

👥 Multiple Readers

🔒 Exclusive Lock

14. SELECT ... FOR UPDATE

Some relational databases support row-locking clauses such as SELECT ... FOR UPDATE. They can be useful when an application reads rows and then intends to update them safely within a transaction.

SQL 
START TRANSACTION;

SELECT balance
FROM accounts
WHERE account_id = 101
FOR UPDATE;

UPDATE accounts
SET balance = balance - 1000
WHERE account_id = 101;

COMMIT;

Exact syntax and behavior vary by DBMS, so always consult the target database documentation.

15. Deadlocks

A deadlock occurs when transactions wait for one another in a cycle and none can continue without intervention.

Transaction A Locks Row 1
→
Wants Row 2 But B owns it
↘
Transaction B Locks Row 2
→
Wants Row 1 But A owns it
A → waits for B → waits for A = DEADLOCK

How Databases Handle Deadlocks

  • Detect the cycle.
  • Choose a transaction as a victim.
  • Roll it back.
  • Allow the other transaction to continue.

How Developers Reduce Deadlocks

  • Access tables and rows in a consistent order.
  • Keep transactions short.
  • Do not hold transactions open unnecessarily.
  • Use appropriate indexes to reduce unnecessary locking work.
  • Retry transactions when the application architecture requires it.

17. Transactions + Constraints

Transactions and constraints work together to protect data integrity.

SQL 
START TRANSACTION;

INSERT INTO students(student_id, name, marks)
VALUES (101, 'Pradeep', 90);

-- This violates a CHECK constraint
INSERT INTO students(student_id, name, marks)
VALUES (102, 'Student B', 150);

ROLLBACK;

If the second operation causes an error, the application can decide whether to roll back the transaction or handle the error and continue, depending on the DBMS and application design.

18. Transactions + Indexes

Indexes can make transactional queries faster, but they also create additional work during INSERT, UPDATE and DELETE operations.

Reads

An appropriate index can help locate rows efficiently.

Writes

Modified indexed columns require index maintenance.

Concurrency

Better query plans can reduce the amount of time resources are held, but indexes do not automatically eliminate locking.

19. Complete Bank Transfer Example

SQL 
START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE account_id = 101
  AND balance >= 1000;

UPDATE accounts
SET balance = balance + 1000
WHERE account_id = 202;

COMMIT;
In a real banking system, application logic should verify that the expected rows were actually updated, handle errors, and use the transaction and locking features appropriate to the DBMS.

21. What Can Cause a Transaction to Fail?

Constraint Error

Duplicate key, foreign-key violation, CHECK failure, etc.

Deadlock

Transactions wait for one another in a cycle.

Connection Failure

The client or database connection unexpectedly terminates.

Timeout

An operation waits longer than the configured limit.

Application Error

The application detects a business-rule failure.

Database Failure

Hardware, process or infrastructure failures can trigger recovery.

22. Transaction Best Practices

  1. Keep transactions as short as practical.
  2. Do not wait for unnecessary user input inside a transaction.
  3. Perform required validation before starting when possible.
  4. Use consistent ordering when updating multiple resources.
  5. Choose isolation levels according to correctness requirements.
  6. Handle deadlocks and transient transaction failures appropriately.
  7. Always define what success and failure mean for the business operation.
  8. Do not assume every DBMS behaves identically.
  9. Test concurrency rather than testing only single-user execution.
  10. Monitor slow transactions and lock waits in production.

25. Exam Preparation

⭐ 5-Mark Answer — What is a Transaction?

A transaction is a logical unit of one or more database operations. It ensures that related operations are handled together. A transaction generally begins with a transaction-start command and ends with COMMIT or ROLLBACK. COMMIT makes successful changes permanent, while ROLLBACK undoes uncommitted changes. Transactions are designed around the ACID properties: Atomicity, Consistency, Isolation and Durability.

⭐ 10-Mark Answer — Explain ACID Properties

  1. Atomicity: A transaction is treated as an all-or-nothing unit.
  2. Consistency: Successful transactions preserve database rules and integrity constraints.
  3. Isolation: Concurrent transactions are controlled according to the selected isolation level.
  4. Durability: Committed changes are preserved through the DBMS recovery and storage mechanisms.

26. Common Mistakes

❌ Mistake 1: Thinking COMMIT can always be undone using ROLLBACK.
❌ Mistake 2: Keeping transactions open while waiting for user input.
❌ Mistake 3: Assuming every database uses the same isolation behavior.
❌ Mistake 4: Ignoring deadlocks in a concurrent application.
❌ Mistake 5: Believing ROLLBACK is a substitute for database backups.
❌ Mistake 6: Assuming a transaction automatically validates every business rule.

27. SQL Transaction Interview Questions

1. What is a transaction?

A logical unit of database work consisting of one or more operations.

2. What does ACID stand for?

Atomicity, Consistency, Isolation and Durability.

3. COMMIT vs ROLLBACK?

COMMIT successfully finishes a transaction; ROLLBACK cancels uncommitted work.

4. What is SAVEPOINT?

A named point inside a transaction that allows partial rollback.

5. What is a dirty read?

Reading data written by another transaction before that transaction has committed.

6. What is a deadlock?

A cyclic waiting situation where transactions hold resources needed by one another.

7. What is the strongest standard isolation level?

Serializable.

8. Why should transactions be short?

Long transactions can increase lock/resource contention, recovery work, latency and the chance of concurrency problems.

9. Does ROLLBACK undo a committed transaction?

No. A committed transaction has completed. Reversal normally requires a new business operation or compensating transaction.

10. Why are transactions important in banking?

They ensure related account updates are handled consistently and protect against partial database updates.
