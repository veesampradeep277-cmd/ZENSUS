🧠 What Is an Index?

An index is a database structure designed to help the database find rows more efficiently without examining every row of the table.

Simple Definition:

An index is like a carefully organized lookup structure that helps the database locate relevant data faster.

📚 Real-World Analogy

Imagine a 1,000-page textbook. You want to find the topic "Binary Search".

Without an index, you might scan page after page.

With the book's index, you can jump directly toward the relevant pages.

🐌 Searching Without an Index

Suppose we have one million students:

SQL 
SELECT *
FROM students
WHERE email = 'arun@example.com';

If there is no useful index and the optimizer chooses a sequential scan, the database may inspect many rows to determine which ones match.

Sequential Scan:

Conceptually, the database examines rows one after another. The exact physical behavior depends on the database engine and execution plan.

⚡ Searching With an Index

Create an index on the searched column:

SQL 
CREATE INDEX idx_students_email
ON students(email);

Now the optimizer may choose an index-based access path for queries involving the indexed column.

Important:

Creating an index does not guarantee that the database will use it. The optimizer chooses a plan based on statistics, cost, selectivity, table size, query structure, and other factors.

🌳 B-Tree Index

B-tree-style indexes are widely used for general-purpose database indexing.

🔍 Equality

Useful for conditions such as:

WHERE id = 100

📏 Range

Useful for:

WHERE salary > 50000

↕️ Ordering

Can help some ORDER BY operations depending on the query and index definition.

🧩 CREATE INDEX Syntax

SQL 
CREATE INDEX index_name
ON table_name(column_name);

Example

SQL 
CREATE INDEX idx_students_name
ON students(name);

1️⃣ Single-Column Index

An index containing one column.

SQL 
CREATE INDEX idx_student_city
ON students(city);

It may help queries such as:

SQL 
SELECT *
FROM students
WHERE city = 'Guntur';

2️⃣ Unique Index

A unique index prevents duplicate indexed key values, subject to the database's NULL semantics.

SQL 
CREATE UNIQUE INDEX idx_unique_email
ON students(email);
UNIQUE Constraint vs Unique Index:

A UNIQUE constraint expresses a data-integrity rule. A unique index is an indexing structure enforcing uniqueness. Database systems may implement a UNIQUE constraint using a unique index, but the concepts are not identical.

3️⃣ Composite Index

A composite index contains multiple columns.

SQL 
CREATE INDEX idx_students_dept_cgpa
ON students(department, cgpa);

It can be useful for queries such as:

SQL 
SELECT *
FROM students
WHERE department = 'CSE'
  AND cgpa >= 8.5;

⭐ Composite Index and Column Order

Column order matters.

Suppose:

Index 
(department, cgpa)

This ordering generally gives the optimizer the best opportunity to use the index when the query constrains the leading department column.

✅ Strong Match 

WHERE department = 'CSE'
AND cgpa >= 8.5

⚠️ Different Pattern 

WHERE cgpa >= 8.5

The index may be less useful because the leading column is not constrained. Exact behavior is optimizer/DBMS dependent.

Interview Term: Leftmost Prefix

For a composite index, the leading columns are especially important. Do not memorize this as an absolute rule for every query; modern optimizers and different index types can behave differently.

🔎 Indexes and WHERE

Indexes are commonly created on columns used frequently in selective filtering.

SQL 
SELECT *
FROM employees
WHERE employee_id = 105;

A primary key normally has an index or index-like access structure in many database systems, but the exact implementation depends on the DBMS.

🔗 Indexes and JOIN

Indexes can be useful on columns participating in joins, especially foreign-key columns and frequently joined keys.

SQL 
SELECT
    s.name,
    d.department_name
FROM students s
JOIN departments d
    ON s.department_id = d.department_id;
Practical Idea:

Indexing the child-side foreign-key column can help joins and can also help some UPDATE/DELETE operations involving the referenced parent key. The exact benefit depends on workload and execution plan.

↕️ Indexes and ORDER BY

An appropriately ordered index may help the database avoid an additional sort operation for some queries.

SQL 
CREATE INDEX idx_students_cgpa
ON students(cgpa DESC);

Query:

SQL 
SELECT student_id, name, cgpa
FROM students
ORDER BY cgpa DESC;
Don't assume:

The optimizer may still choose a sort or another plan if it estimates that doing so is cheaper.

📏 Range Queries

B-tree-style indexes are particularly useful for ordered ranges.

SQL 
SELECT *
FROM products
WHERE price BETWEEN 1000 AND 5000;

An index on price may provide an efficient way to locate the relevant range.

🎯 Selectivity

Selectivity describes how effectively a condition narrows down the possible rows.

High Selectivity

Example: 

WHERE email = 'a@b.com'

Usually only a tiny number of rows match.

Low Selectivity

Example: 

WHERE gender = 'M'

If a large percentage of rows match, an index may provide less benefit.

Important:

Selectivity is only one factor. Table size, data distribution, statistics, cost estimates, cache state, query shape, and the DBMS optimizer all influence the final plan.

🚀 Covering Index

A covering index contains enough indexed information for a query to be satisfied without needing to fetch the full table row, when the DBMS and index structure support that access path.

SQL 
CREATE INDEX idx_student_lookup
ON students(department, cgpa, name);

Query:

SQL 
SELECT name, cgpa
FROM students
WHERE department = 'CSE'
  AND cgpa >= 9.0;
Trade-off:

Adding more columns to an index makes the index larger and can increase storage and write-maintenance cost.

🧩 Partial / Filtered Index

Some database systems allow indexes to cover only rows satisfying a condition.

PostgreSQL-style Example

SQL 
CREATE INDEX idx_active_users
ON users(email)
WHERE status = 'active';

This can be useful when only a subset of a table is frequently queried.

Dialect Note:

Partial/filtered index syntax and support differ across database systems.

🧮 Expression / Functional Index

Some database systems support indexes on expressions rather than only raw column values.

Example

SQL 
CREATE INDEX idx_lower_email
ON users (LOWER(email));

This can support searches such as:

SQL 
SELECT *
FROM users
WHERE LOWER(email) = 'arun@example.com';
DBMS-specific:

Expression-index syntax and capabilities differ across database systems.

#️⃣ Hash Index

Hash-based indexing can provide efficient equality lookups in database systems that support it.

PostgreSQL-style example 
CREATE INDEX idx_users_email_hash
ON users USING HASH(email);

🔤 Specialized Indexes

Modern database systems can provide specialized indexing methods for particular workloads.

🔤 Full Text

Designed for searching words and textual content.

🗺️ Spatial

Useful for geographic and geometric data.

🧱 GIN / GiST

PostgreSQL provides specialized index methods such as GIN and GiST for particular data types and operators.

Interview Tip:

Don't claim that one index type is "best". The correct index depends on the query workload, data type, operators, and DBMS.

NULL and Indexes

Index behavior involving NULL values depends on the database system and index type.

For example:

SQL 
SELECT *
FROM students
WHERE email IS NULL;

Whether and how efficiently an index is used for NULL predicates depends on the DBMS and index design.

⚖️ The Cost of Indexes

Indexes are not free.

✅ Advantages

  • Faster selective lookups
  • Can improve joins
  • Can help ORDER BY
  • Can help range queries
  • Can enforce uniqueness

❌ Costs

  • Consumes storage
  • INSERT can become more expensive
  • UPDATE can become more expensive
  • DELETE can become more expensive
  • Too many indexes complicate maintenance
Golden Rule:

Don't create an index for every column. Indexes should be designed from actual query and workload requirements.

🔑 Primary Keys and Indexes

SQL 
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255)
);

In many relational database systems, a primary key is backed by an index or index-like structure to enforce uniqueness and support efficient lookup.

Don't create redundant indexes blindly.

If a primary key already provides the required index structure, creating another identical index is usually unnecessary.

🔗 Foreign Keys and Indexes

Consider:

SQL 
CREATE TABLE students (
    student_id INT PRIMARY KEY,
    department_id INT,

    FOREIGN KEY (department_id)
        REFERENCES departments(department_id)
);

Indexing students.department_id can often be beneficial for joins and for operations involving the referenced parent rows.

Important:

A foreign key does not necessarily cause every DBMS to automatically create an index on the child column.

🗑️ DROP INDEX

Index removal syntax varies by DBMS.

PostgreSQL / many systems

SQL 
DROP INDEX idx_students_email;
Dialect Difference:

MySQL, SQL Server, Oracle, PostgreSQL, and SQLite have differences in CREATE/DROP INDEX syntax and index management. Learn the syntax for the database you are actually using.

🔬 EXPLAIN — See the Query Plan

Instead of guessing whether an index helps, inspect the query execution plan.

PostgreSQL / MySQL-style concept 
EXPLAIN
SELECT *
FROM students
WHERE email = 'arun@example.com';

Some database systems also support commands such as EXPLAIN ANALYZE or related features to inspect actual execution behavior.

🔎 Scan

What access method is being used?

💰 Cost

What estimated work does the optimizer expect?

📊 Rows

How many rows are estimated or actually processed?

⚠️ Functions Can Affect Index Usage

Consider:

SQL

FROM users

A simple index on email may not be directly usable for this expression in some database systems.

An expression index may solve this when supported:

SQL 
CREATE INDEX idx_lower_email
ON users(LOWER(email));

🚫 When Should You Avoid an Index?

  • Very small tables where scanning is already cheap.
  • Columns rarely used for filtering, joining, ordering, or uniqueness.
  • Columns with poor usefulness for the workload.
  • Excessive indexes on write-heavy tables.
  • Duplicate or redundant indexes.
Remember:

"More indexes" does not mean "more performance".

♻️ Redundant Indexes

Suppose you already have:

Index A 
(department, cgpa)

Creating another index with the exact same key order may provide little or no additional benefit and increases maintenance cost.

Professional Rule:

Audit existing indexes before creating new ones.

🏆 Index Best Practices

  1. Index based on real workload, not assumptions.
  2. Inspect execution plans.
  3. Prefer meaningful composite indexes for recurring query patterns.
  4. Carefully choose column order in composite indexes.
  5. Avoid unnecessary duplicate indexes.
  6. Remember write overhead.
  7. Consider foreign-key columns used heavily in joins.
  8. Use specialized indexes only when their workload justifies them.
  9. Monitor index size and usage.
  10. Re-evaluate indexes as application workloads change.

⚠️ Common Index Mistakes

❌ Mistake 1

Creating indexes on every column.

Fix:

Index based on workload.

❌ Mistake 2

Assuming an index is always used.

Fix:

Check EXPLAIN.

❌ Mistake 3

Ignoring composite column order.

Fix:

Design the index around common predicates and ordering.

❌ Mistake 4

Forgetting INSERT/UPDATE/DELETE overhead.

Fix:

Balance read performance with write cost.

❌ Mistake 5

Creating duplicate indexes.

Fix:

Audit existing indexes.

❌ Mistake 6

Assuming syntax is identical across all databases.

Fix:

Learn your DBMS dialect.

Question:

What is an index in SQL? Explain its advantages.

Answer

An index is a database data structure used to improve the efficiency of data retrieval. It allows the database to locate relevant rows without necessarily scanning the entire table.

Indexes can improve:

  • SELECT queries
  • WHERE filtering
  • JOIN operations
  • ORDER BY operations
  • Range searches

However, indexes require storage and can increase the cost of INSERT, UPDATE, and DELETE operations.

🎤 Interview Questions

1. What is an index?

An index is a database structure that can provide a more efficient access path to rows for suitable queries.

2. Why do indexes improve query performance?

They can allow the database to locate relevant entries without scanning all table rows, reducing the amount of work for suitable queries.

3. What is the disadvantage of indexes?

They consume storage and require maintenance during INSERT, UPDATE, and DELETE operations.

4. What is a composite index?

An index containing multiple columns, such as (department, cgpa).

5. Why does column order matter?

Composite indexes are ordered by their key columns, so the leading columns strongly influence which query predicates can efficiently use the index.

6. What is selectivity?

Selectivity describes how effectively a predicate narrows the possible rows. Highly selective predicates often make indexes more attractive.

7. What is a covering index?

An index containing enough information for a query to be satisfied from the index access path without fetching the full table row, where supported and chosen by the optimizer.

8. Does an index guarantee faster queries?

No. The optimizer chooses the execution plan based on cost, statistics, data distribution, query shape, and other factors.

9. Why can an index slow INSERT?

The database may need to update the index structures whenever indexed values change or new rows are inserted.

10. What is EXPLAIN?

EXPLAIN is used to inspect how a database plans to execute a query. Exact output and syntax vary by DBMS.

11. Should foreign-key columns be indexed?

Often yes when they are frequently used for joins or parent-row modifications, but the decision should be based on workload and execution plans.

12. B-tree vs Hash index?

B-tree indexes support a broad set of ordered operations, including equality and ranges. Hash indexes are specialized primarily for equality access where supported.
