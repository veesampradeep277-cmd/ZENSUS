🧠 What Is a View?

A View is a named SQL query that behaves like a virtual table. It usually does not store a separate copy of the underlying data. Instead, the database stores the View definition and retrieves data from its underlying tables when the View is queried.

Simple Definition:

A View is a saved query that can be accessed like a table.

🌍 Real-World Analogy

Imagine a college database containing thousands of student records. A faculty member may only need:

  • Student name
  • Department
  • CGPA

They don't need access to every sensitive field such as phone number, personal address, or other private information.

Solution:

Create a View containing only the required columns.

🧩 CREATE VIEW — Basic Syntax

SQL 
CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;

Example

SQL 
CREATE VIEW cse_students AS
SELECT student_id, name, cgpa
FROM students
WHERE department = 'CSE';

Now the View can be queried almost like a table:

SQL 
SELECT *
FROM cse_students;

🚀 Why Do We Use Views?

🔒 Security

Expose only the columns and rows a user needs.

♻️ Reusability

Save complex queries and reuse them.

🧹 Simplicity

Hide complicated JOINs and calculations.

🛠️ Abstraction

Users can work with a simplified database interface.

📊 Reporting

Create reusable reporting datasets.

🔄 Consistency

Centralize commonly used query logic.

🔐 Creating a Security View

Suppose the original table contains sensitive email information. We can create a View containing only public student information.

SQL 
CREATE VIEW public_students AS
SELECT student_id, name, department, cgpa
FROM students;
Security Principle

A View can reduce unnecessary exposure, but a View alone is not a complete security system. Proper database privileges, authentication, authorization, and row/column controls may also be required.

🔎 View with WHERE

SQL 
CREATE VIEW toppers AS
SELECT student_id, name, cgpa
FROM students
WHERE cgpa >= 9.0;

Query it:

SQL 
SELECT *
FROM toppers
ORDER BY cgpa DESC;

🔗 View with JOIN

Views become extremely useful when a query contains multiple tables.

SQL 
CREATE VIEW student_department AS
SELECT
    s.student_id,
    s.name,
    d.department_name
FROM students s
JOIN departments d
    ON s.department_id = d.department_id;

Instead of writing the JOIN repeatedly:

SQL 
SELECT *
FROM student_department;

📊 View with GROUP BY and Aggregate Functions

SQL 
CREATE VIEW department_statistics AS
SELECT
    department,
    COUNT(*) AS student_count,
    AVG(cgpa) AS average_cgpa,
    MAX(cgpa) AS highest_cgpa
FROM students
GROUP BY department;

Then:

SQL 
SELECT *
FROM department_statistics
ORDER BY average_cgpa DESC;

🔄 Replacing a View

If the View definition needs to change, many database systems support:

SQL 
CREATE OR REPLACE VIEW toppers AS
SELECT student_id, name, department, cgpa
FROM students
WHERE cgpa >= 8.5;
Important:

View-management syntax varies across database systems. Always check the SQL dialect you are using.

🗑️ DROP VIEW

To remove a View:

SQL 
DROP VIEW toppers;

Some database systems support:

SQL 
DROP VIEW IF EXISTS toppers;
Remember:

Dropping a View removes the View definition. It does not normally delete the underlying table data.

✏️ Updatable Views

Some Views can allow INSERT, UPDATE, or DELETE operations that affect the underlying table.

For example, a simple View based on one table may be updatable depending on the database system and View definition.

SQL 
CREATE VIEW cse_students AS
SELECT student_id, name, cgpa
FROM students
WHERE department = 'CSE';

In a database that permits updates through this View:

SQL 
UPDATE cse_students
SET cgpa = 9.5
WHERE student_id = 101;
Important:

Not every View is updatable. JOINs, GROUP BY, DISTINCT, aggregate functions, UNION, calculated columns, and other constructs can make a View non-updatable depending on the database system.

🏢 Professional Reporting View

Imagine a company has:

  • Employees
  • Departments
  • Projects
  • Salary information

A reporting team may need a simplified employee dashboard.

SQL 
CREATE VIEW employee_report AS
SELECT
    e.employee_id,
    e.employee_name,
    d.department_name,
    e.salary
FROM employees e
JOIN departments d
    ON e.department_id = d.department_id;

Application developers can then write:

SQL 
SELECT *
FROM employee_report
WHERE salary > 60000
ORDER BY salary DESC;

🪆 Views Based on Other Views

Some database systems allow a View to reference another View.

SQL 
CREATE VIEW cse_students AS
SELECT student_id, name, cgpa
FROM students
WHERE department = 'CSE';

CREATE VIEW excellent_cse_students AS
SELECT student_id, name, cgpa
FROM cse_students
WHERE cgpa >= 9.0;
Design Warning:

Deep chains of Views can become difficult to understand, debug, and optimize. Keep the dependency structure clean.

⚡ Materialized Views

A normal View generally represents a query definition. A Materialized View stores the result of a query physically and can be refreshed later.

Normal View

  • Usually does not store separate result data
  • Reflects current underlying data when queried
  • Useful for abstraction and security

Materialized View

  • Stores query results
  • Can speed up expensive reports
  • Needs refresh strategy
Database-specific feature:

Materialized View syntax and refresh behavior vary significantly between database systems.

⚡ Views and Performance

A View is not automatically faster than the query it represents. It is primarily an abstraction mechanism.

1️⃣ Query Complexity

Complex View definitions may still require expensive joins or aggregations.

2️⃣ Indexes

Indexes on underlying tables may help the optimizer execute View queries efficiently.

3️⃣ EXPLAIN

Use your database's EXPLAIN tools to understand the actual execution plan.

Golden Rule:

Don't assume a View improves performance just because it makes SQL shorter. Measure the actual query plan.

⚠️ Common Mistakes

❌ Mistake 1

Thinking a normal View always stores a separate copy of the data.

Fix:

Understand the difference between a normal View and a materialized View.

❌ Mistake 2

Assuming Views automatically improve performance.

Fix:

Check the execution plan and indexes.

❌ Mistake 3

Assuming every View is updateable.

Fix:

Complex Views may not support modifications.

❌ Mistake 4

Creating too many deeply dependent Views.

Fix:

Keep View dependencies simple and documented.

❌ Mistake 5

Treating Views as complete security by themselves.

Fix:

Combine Views with database permissions and proper authorization.

❌ Mistake 6

Forgetting that View behavior can differ between DBMSs.

Fix:

Always verify dialect-specific syntax and restrictions.

🏆 Professional Best Practices

  1. Use meaningful View names.
  2. Document the purpose of important Views.
  3. Avoid unnecessary SELECT * in production Views.
  4. Expose only the columns required by consumers.
  5. Keep View dependencies manageable.
  6. Review View performance with execution plans.
  7. Use indexes on underlying tables where appropriate.
  8. Don't use Views as a substitute for proper authorization.
  9. Understand how schema changes affect View dependencies.
  10. Test Views after changes to underlying tables.

🎤 Interview Questions

1. What is a View?

A View is a named database object representing the result of a stored SELECT query and is generally queried like a virtual table.

2. Does a normal View store data?

Usually it stores the query definition rather than an independent copy of the result data. Materialized Views are different.

3. Why use Views?

For abstraction, reuse, reporting, simplified queries, and controlled exposure of data.

4. Can we update a View?

Some simple Views can be updated, but updateability depends on the View definition and DBMS.

5. Can a View contain JOINs?

Yes. Views can be defined using joins, although such Views may have restrictions on updateability.

6. What is a Materialized View?

A Materialized View stores the result of a query physically and typically requires refreshing when the underlying data changes.

7. View vs Table?

A table primarily stores data, while a normal View primarily stores a query definition and presents derived data.

8. Does a View improve performance?

Not automatically. A normal View is primarily an abstraction mechanism. Performance depends on the resulting query plan, indexes, optimizer, and database system.

9. Can a View reference another View?

Many database systems allow View dependencies, although excessive nesting can make systems difficult to maintain.

10. How do you delete a View?

Use DROP VIEW, subject to the syntax and dependency rules of the database system.
