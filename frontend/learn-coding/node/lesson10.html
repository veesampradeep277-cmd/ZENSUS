What is Middleware?

The core concept behind Express request processing

Middleware is a function that runs during the request-response cycle of an Express application.

A middleware function has access to the request object req, the response object res, and a function called next.

Basic Middleware Structure 
app.use((req, res, next) => {
  console.log("Middleware executed");

  next();
});

What does each part mean?

Part Meaning
req Contains information about the incoming HTTP request.
res Used to send a response back to the client.
next Passes control to the next middleware or route handler.
Important: A middleware function must either finish the request by sending a response, or pass control onward using next().
Common mistake: If middleware neither sends a response nor calls next(), the request can remain pending.
03

Middleware Request Flow

Understand what happens to a request

Express processes a request through a sequence of middleware and route handlers.

Client Browser / App
→
Middleware 1 Logger
→
Middleware 2 Auth
→
Route Controller
→
Response JSON / HTML

The role of next()

next() tells Express: "I have finished my middleware work. Continue processing this request."

next() Example 
app.use((req, res, next) => {

  console.log("Step 1");

  next();

});

app.use((req, res, next) => {

  console.log("Step 2");

  next();

});

app.get("/", (req, res) => {

  res.send("Final route");

});
Execution order: Step 1 → Step 2 → Route → Response
04

app.use()

The most common way to register middleware

Express provides app.use() to attach middleware to the application.

Global Middleware 
const express = require("express");

const app = express();

app.use((req, res, next) => {

  console.log("Request received");

  next();

});

Without a path, this middleware can run for incoming requests handled by the application, subject to normal Express routing behavior.

Middleware with a path

Path-specific Middleware 
app.use("/admin", (req, res, next) => {

  console.log("Admin middleware");

  next();

});

This middleware is applied when the request path begins with /admin.

05

Types of Middleware

Different middleware has different responsibilities

1

Application-level

Attached to the Express application using app.use() or HTTP-method functions.

2

Router-level

Attached to an Express Router and normally used to organize route-specific behavior.

3

Built-in

Middleware supplied by Express, such as express.json() and express.static().

4

Third-party

Middleware provided by external packages, such as logging or security-related packages.

5

Custom

Middleware written by the developer for application-specific requirements.

6

Error-handling

Special middleware used to process errors and generate consistent error responses.

06

Route-Level Middleware

Protect or prepare specific routes

Not every middleware needs to run for every request. Route-level middleware can be used when only a particular route requires a specific operation.

Authentication Example 
function checkAuth(req, res, next) {

  const authenticated = true;

  if (authenticated) {
    next();
  } else {
    res.status(401).json({
      message: "Authentication required"
    });
  }

}

app.get("/dashboard", checkAuth, (req, res) => {

  res.json({
    message: "Welcome to dashboard"
  });

});
The route handler runs only if checkAuth calls next().

Middleware Parameters

Understanding req, res and next

1. req — Request

The request object contains information sent by the client.

Request Information 
app.use((req, res, next) => {

  console.log(req.method);

  console.log(req.headers);

  next();

2. res — Response

The response object is used to send data back to the client.

Response 
res.status(200).json({
  message: "Success"
});

3. next — Continue

next() 
next();

Calling next() moves processing to the next matching middleware or route handler.

Built-in Express Middleware

Middleware provided directly by Express

express.json()

This middleware parses incoming requests containing JSON payloads and makes the parsed data available through req.body.

JSON Parser 
const express = require("express");

const app = express();

app.use(express.json());

app.post("/users", (req, res) => {

  console.log(req.body);

  res.json({
    received: req.body
  });

});

express.urlencoded()

Parses URL-encoded form data.

URL Encoded Data 
app.use(express.urlencoded({
  extended: true
}));

express.static()

Serves static files such as HTML, CSS, JavaScript and images.

Static Files 
app.use(express.static("public"));

Creating Custom Middleware

Build reusable application logic

Example: Request Logger

logger.js 
function logger(req, res, next) {

  const time = new Date().toISOString();

  console.log(
    `${time} ${req.method} ${req.url}`
  );

  next();
}

module.exports = logger;

Then use it in the main application:

app.js 
const express = require("express");
const logger = require("./logger");

const app = express();

app.use(logger);

app.get("/", (req, res) => {
  res.send("Home");
});

app.listen(3000);
Custom middleware is useful for logging, authentication, authorization, validation, rate limiting, request transformation, and many other application concerns.

Error Handling in Express

What happens when something goes wrong?

An error can occur because of invalid input, missing resources, authentication problems, database failures, programming bugs, external service failures, or unexpected conditions.

A production application should not expose raw internal errors to users. Instead, errors should be handled centrally and converted into appropriate HTTP responses.

Basic error response

Simple Error 
app.get("/profile", (req, res) => {

  const user = null;

  if (!user) {
    return res.status(404).json({
      error: "User not found"
    });
  }

  res.json(user);

});
12

Error-Handling Middleware

The special four-parameter middleware function

Express recognizes error-handling middleware by its four parameters:

Error Middleware Structure 
app.use((err, req, res, next) => {

  console.error(err);

  res.status(500).json({
    error: "Something went wrong"
  });

});
Parameter Purpose
err The error object.
req The incoming request.
res The response that will be sent to the client.
next Passes the error to another error handler.
Important: Error-handling middleware should normally be registered after your routes and other middleware so it can receive errors passed through the middleware chain.

Using next(error)

Passing an Error 
app.get("/data", (req, res, next) => {

  const error = new Error(
    "Database connection failed"
  );

  next(error);

});

When next(error) is called, Express skips regular middleware and moves toward error-handling middleware.

Conceptually: next() → continue normally
next(error) → enter error-handling flow

Important distinction

Calling next() does not mean "send a response." It only passes control onward.

Calling res.json(), res.send() or res.end() sends the response and normally finishes request processing.

14

Handling Asynchronous Errors

Promises, async/await and rejected operations

Modern Express applications frequently perform asynchronous operations such as database queries, API calls and file operations.

Async Route Example 
app.get("/users", async (req, res, next) => {

  try {

    const users = await getUsers();

    res.json(users);

  } catch (error) {

    next(error);

  }

});

The try/catch ensures that a rejected asynchronous operation can be passed to the centralized error handler.

Always consider how rejected promises and asynchronous failures reach your application's error-handling path. Do not assume every async failure is automatically handled in every Express version or coding pattern.

Middleware & Error Handling Best Practices

How professional Express applications are structured

Keep middleware focused

A middleware function should generally perform one clear responsibility rather than becoming a large collection of unrelated operations.

Call next() deliberately

Do not call next() after you have already sent a response unless you have a specific reason and understand the flow.

Centralize error handling

A centralized error handler makes API responses more consistent and simplifies logging and maintenance.

Do not expose internals

Avoid sending database details, stack traces or secrets to production clients.

Validate input

Validate request body, parameters and query values before using them in application logic.

Use appropriate status codes

Status codes help clients understand whether a request succeeded, failed due to input, or failed on the server.

Middleware in the Request Lifecycle

Connecting Express concepts together

A useful mental model is to treat middleware as a processing pipeline.

Complete Request Pipeline 
Client
   ↓
Express receives request
   ↓
Logger middleware
   ↓
Authentication middleware
   ↓
Validation middleware
   ↓
Route handler
   ↓
Database / business logic
   ↓
Response
   ↓
Client

If a middleware detects a problem, it can stop normal processing and either send an appropriate response or pass an error into the error-handling pipeline.

Mini Project — Production-Style API Flow

Combine logging, authentication, validation and error handling

server.js 
const express = require("express");

const app = express();

app.use(express.json());

/* Logger */
function logger(req, res, next) {

  console.log(
    `${req.method} ${req.url}`
  );

  next();
}

/* Authentication */
function authenticate(req, res, next) {

  const token = req.headers.authorization;

  if (!token) {
    return res.status(401).json({
      error: "Authentication required"
    });
  }

  next();
}

/* Validation */
function validateUser(req, res, next) {

  const { name, email } = req.body;

  if (!name || !email) {
    return res.status(400).json({
      error: "Name and email are required"
    });
  }

  next();
}

app.use(logger);

app.post(
  "/users",
  authenticate,
  validateUser,
  (req, res) => {

    res.status(201).json({
      message: "User created",
      user: req.body
    });

  }
);

/* 404 handler */
app.use((req, res) => {

  res.status(404).json({
    error: "Route not found"
  });

});

/* Central error handler */
app.use((err, req, res, next) => {

  console.error(err);

  res.status(500).json({
    error: "Internal server error"
  });

});

app.listen(3000, () => {

  console.log(
    "Server running on port 3000"
  );

});

What happens here?

  1. Express parses JSON using express.json().
  2. The logger records the request.
  3. Authentication checks the request.
  4. Validation checks the submitted user data.
  5. The route creates the response.
  6. Unknown routes reach the 404 handler.
  7. Unexpected errors can reach the central error handler.
This pattern separates concerns and makes the application easier to maintain as it grows.

Common Middleware Mistakes

Problems beginners frequently encounter

If middleware neither sends a response nor calls next(), processing can stop and the request may remain pending.
Once you have completed the response, continuing the normal pipeline can lead to unexpected behavior or "headers already sent" errors.
Error-handling middleware uses four parameters: (err, req, res, next).
Middleware order matters. A middleware generally only affects requests that reach it in the pipeline.
Detailed stack traces are useful during development but should be handled carefully in production responses.

Interview Questions

Important Express.js questions

Middleware is a function that participates in the request- response cycle and can access req, res and next.
It passes control to the next matching middleware or route handler.
If the middleware does not send a response either, the request can remain unresolved.
It is middleware with the signature (err, req, res, next) that handles errors passed through the Express pipeline.
Express processes middleware and routes in their registered order, so placing middleware before or after a route changes which requests it can affect.
It is built-in Express middleware that parses JSON request bodies and exposes the parsed data through req.body.
Call next(error) so Express can enter its error-handling flow.
401 indicates that authentication is required or invalid, while 403 indicates that the server understood the request but access is not allowed.
