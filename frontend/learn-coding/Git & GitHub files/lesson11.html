Pull Requests & Code Review

Learn how developers propose changes, review code, discuss improvements, request changes, approve work, and safely merge contributions into a shared repository.

1. What Is a Pull Request?

A Pull Request (PR) is a GitHub feature used to propose changes from one branch into another branch.

A pull request allows developers to show their changes, explain what they changed, and ask other developers to review the work before it becomes part of the target branch.

Feature Branch Your changes
→
Pull Request Review proposed
→
Code Review Feedback
→
Target Branch main
Important:

A pull request is not the same thing as git pull.

git pull is a Git command used to retrieve and integrate remote changes.
A Pull Request is a GitHub collaboration mechanism for proposing changes.

2. Why Do We Use Pull Requests?

👀 Review Changes

Other developers can inspect the code before it is merged.

💬 Discuss Code

Developers can discuss implementation decisions directly on the proposed changes.

🛡️ Protect Main

Teams can require review and automated checks before changes reach important branches.

📝 Document Work

The PR provides a record of what changed and why.

🧪 Run Checks

Automated tests and CI checks can run against proposed changes.

🤝 Team Collaboration

Multiple developers can contribute without directly changing the main branch at the same time.

3. Anatomy of a Pull Request

A pull request normally contains several useful pieces of information.

Open
Add student search feature
feature/student-search → main

Description

Adds a search field to the student management page. Users can now search students by name.

Changes

  • Added search input
  • Added filtering logic
  • Updated UI
  • Added tests

Reviewers

Backend developer, frontend developer

PR Element Purpose
Title Quickly explains the change
Description Explains what and why
Source branch Branch containing the proposed changes
Target branch Branch that may receive the changes
Reviewers People asked to inspect the changes
Checks Automated tests and other validations

4. Creating a Pull Request

A typical feature workflow begins by creating a separate branch. 

git switch main

git pull origin main

git switch -c feature/student-search

Make your changes, then commit them. 

git add .

git commit -m "Add student search feature"

Push the branch to GitHub. 

git push -u origin feature/student-search

GitHub can then display an option to create a pull request from your branch.

5. What Is Code Review?

Code review is the process of examining another developer's code before it is accepted into a shared codebase.

Pull Request

The mechanism used to propose the changes.

Code Review

The process of examining and discussing those changes.

Reviewers may check

  • Does the code solve the intended problem?
  • Is the code readable?
  • Are there bugs or edge cases?
  • Are tests included where appropriate?
  • Does the change follow project conventions?
  • Could the implementation introduce security problems?
  • Does the change affect existing functionality?

6. Typical Code Review Process

→

→
Feedback Comments
→

→
Approval Ready to merge

Possible review outcomes

Outcome Meaning
Comment Reviewer is providing feedback or asking a question.
Request changes Changes should be made before approval.
Approve Reviewer is satisfied with the proposed changes.

7. Writing Good Review Comments

Good code review comments should focus on the code and provide useful reasoning.

Reviewer
Could we validate the input before calling the database? This would prevent invalid values from reaching the query.
Reviewer
Would a function make this repeated logic easier to test and reuse?
Reviewer
Please add a test for the empty-input case.
Good review principle: Critique the implementation, not the person.

8. Handling Review Feedback

If a reviewer requests a change, you normally make the correction on the same branch used by the pull request. 

# Make requested changes

git status

git add .

git commit -m "Address review feedback"

git push

Because the pull request is connected to the branch, the new commit can appear in the existing pull request.

PR Review feedback
→
Edit Fix issue
→
Commit Save fix
→
Push Update PR

9. Merging a Pull Request

Once the required reviews and checks are complete, an authorized person can merge the pull request according to the repository's rules.

GitHub commonly provides several merge strategies.

Strategy General idea
Create a merge commit Combines the histories with a merge commit.
Squash and merge Combines the pull request's commits into a single commit on the target branch.
Rebase and merge Replays commits on top of the target branch to produce a linear history.
Important: The available merge methods and branch rules depend on the repository's GitHub settings.

11. Pull Request Best Practices

Keep PRs Focused

A pull request should ideally address a clear, understandable change.

Write a Clear Title

Explain the main purpose of the change.

Explain Why

Include useful context in the description.

Test Before PR

Run relevant tests locally before asking others to review the code.

Review Carefully

Read the actual code changes instead of approving without inspection.

Respond to Feedback

Discuss comments and make requested changes when appropriate.

12. Common Pull Request Mistakes

Huge PRs

Very large unrelated changes make review difficult.

Weak Description

Reviewers may not understand what the change is supposed to accomplish.

No Testing

Untested changes can introduce regressions.

Direct Main Changes

Teams often use protected branches and PR workflows instead of directly committing to important branches.

Ignoring Feedback

Review comments should be understood and addressed or discussed.

Mixing Unrelated Work

Separate unrelated features into separate branches and pull requests.

13. Complete Example

Imagine you are adding a login feature to a web application.

Step 1 — Update main 

git switch main

git pull origin main

Step 2 — Create feature branch 

git switch -c feature/login

Step 3 — Develop 

# edit files

git status

Step 4 — Commit 

git add .

git commit -m "Add user login"

Step 5 — Push 

git push -u origin feature/login

Step 6 — Open Pull Request

On GitHub, create a pull request from feature/login into main.

Step 7 — Review

Reviewers inspect the code, tests, security considerations, and overall implementation.

Step 8 — Fix feedback 

git add .

git commit -m "Address login review feedback"

git push

Step 9 — Merge

After the required checks and reviews are complete, the PR can be merged according to the repository rules.

17. Lesson Takeaway

Pull requests and code reviews are central to collaborative software development.

  • A Pull Request proposes changes from one branch into another.
  • A pull request is different from the git pull command.
  • Code review allows other developers to inspect and discuss proposed changes.
  • Reviewers can comment, request changes, or approve a PR.
  • Developers normally update the same feature branch when addressing review feedback.
  • Automated tests and checks can help validate a PR.
  • Teams may protect important branches such as main.
  • Pull requests provide a useful record of discussions and changes.
  • Good PRs are focused, clearly described, tested, and easy for reviewers to understand.
