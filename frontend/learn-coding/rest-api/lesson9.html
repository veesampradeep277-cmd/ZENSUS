Building GET & POST APIs

Learn how to build APIs that retrieve data with GET and create new data with POST. Understand endpoints, request bodies, JSON, query parameters, validation, responses, status codes, and the complete client-to-server flow.

01

GET & POST — The Foundation

GET and POST are two of the most commonly used HTTP methods when building REST APIs.

GET

Retrieve Data

GET requests are used when a client wants to retrieve information from the server.

Example 
GET /students/
POST

Create Data

POST requests are commonly used when a client wants to submit data to create a new resource.

Example 
POST /students/
Easy way to remember:

GET → "Give me the data."
POST → "Here is some data. Create something with it."
02

Building a GET API

A GET API receives a request and returns data to the client.

Basic GET Endpoint

Endpoint 
GET /students/

A client could request this endpoint from a browser, frontend application, mobile application, Postman, or another service.

Example JSON Response

Response 
[
    {
        "id": 101,
        "name": "Pradeep",
        "course": "REST API"
    },
    {
        "id": 102,
        "name": "Anjali",
        "course": "Python"
    }
]
Important:

A GET request normally does not require a request body for retrieving resources. Parameters needed to identify or filter resources are commonly placed in the URL.
03

GET — Retrieve All Data

Suppose an application contains many students. To retrieve the student collection, the client can send:

HTTP Request 
GET /students/

Server Processing

1

2

3
Query Data

4

The application prepares the data in a format such as JSON.

5
Return Response

The server returns the data to the client.

04

GET — Retrieve One Resource

To retrieve one specific student, the student's ID can be included in the URL.

Individual Resource 
GET /students/101/

Here, 101 identifies the student.

Example Response

JSON Response 
{
    "id": 101,
    "name": "Pradeep",
    "email": "pradeep@example.com",
    "age": 21,
    "course": "REST API"
}

What if Student 101 Does Not Exist?

404 Not Found 
{
    "error": "Student not found",
    "code": "STUDENT_NOT_FOUND"
}
The API should clearly tell the client whether the requested resource exists.
05

GET with Query Parameters

Query parameters allow a client to provide additional information to a GET request.

Example

Query Parameter 
GET /students/?course=Python

Here:

  • /students/ is the endpoint.
  • ? starts the query parameters.
  • course=Python is a parameter.

Multiple Parameters

Filtering 
GET /students/?course=Python&age=21

Query parameters can be used for filtering, searching, sorting, pagination, and other request options depending on the API design.

Remember:

Query parameters are part of the URL. They are not the same thing as a JSON request body.

Understanding the POST Request Body

The request body contains the data that the client wants to send to the server.

Example HTTP Request

POST Request 
POST /students/ HTTP/1.1
Content-Type: application/json

{
    "name": "Rahul",
    "email": "rahul@example.com",
    "age": 22,
    "course": "Django"
}

Important Parts

📍

Method

POST tells the server what kind of operation is requested.

🔗

URL

The URL identifies the API resource.

📦

Headers

Headers provide additional information about the request.

📝

Body

The body contains the data being submitted.

Content-Type

When JSON is sent in the request body, the client commonly uses:

Header

08

Validation in POST APIs

The server should validate incoming data before storing it.

Invalid Request

Bad Data 
{
    "name": "",
    "email": "wrong-email",
    "age": -4
}

Possible Validation Rules

  • Name should not be empty.
  • Email should have a valid format.
  • Age should satisfy the application's allowed range.
  • Required fields should be present.
  • Duplicate values should be handled according to application rules.

Validation Error

400 Bad Request 
{
    "error": "Validation failed",
    "fields": {
        "name": "This field is required.",
        "email": "Enter a valid email address.",
        "age": "Age is invalid."
    }
}
Best practice:

Return useful validation information so the client knows what needs to be corrected.
09

GET & POST Responses

Every API request should result in an HTTP response. The response normally contains a status code, headers, and sometimes a response body.

GET RESPONSE 
HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 101,
    "name": "Pradeep",
    "course": "REST API"
}
POST RESPONSE 
HTTP/1.1 201 Created
Content-Type: application/json

{
    "id": 104,
    "name": "Rahul",
    "course": "Django"
}

Common Status Codes

Code Meaning Typical Situation
200 OK Successful GET request
201 Created Successful POST that creates a resource
400 Bad Request Invalid input
401 Unauthorized Authentication required or failed
403 Forbidden Permission denied
404 Not Found Resource does not exist
500 Internal Server Error Unexpected server-side problem

GET vs POST

Feature GET POST
Purpose Retrieve data Submit/create data
Common URL /students/ /students/
Request body Normally not used for retrieval Commonly used
Query parameters Commonly used Possible, depending on API design
Changes server state? Normally should not Often does
Typical success 200 OK 201 Created
Example Get students Create student
Important REST idea:

GET is intended for retrieving representations of resources and should not be designed to perform ordinary data-creation or data-modification actions.

Common GET & POST Errors

1. Wrong Endpoint

Incorrect 
GET /student/
Expected Example 
GET /students/

2. Missing Content-Type

When sending JSON in a POST request, the client should correctly identify the content type.

Header 
Content-Type: application/json

3. Invalid JSON

Invalid 
{
    "name": "Rahul",
    "age": 22,
}

The trailing comma makes this invalid JSON.

4. Missing Required Field

Invalid POST 
{
    "name": "Rahul"
}

If the API requires email, age and course, the server should return a validation error instead of silently accepting incomplete data.

5. Resource Not Found

404 
GET /students/9999/
If student 9999 does not exist, the API should normally return a suitable 404 Not Found response.

Lesson Takeaway

  • GET is commonly used to retrieve resources.
  • POST is commonly used to submit data and create new resources.
  • GET commonly uses URL paths and query parameters to identify or filter requested data.
  • POST commonly carries submitted data in the request body.
  • JSON is commonly used for API request and response data.
  • Content-Type: application/json identifies a JSON request body.
  • A successful GET commonly returns 200 OK.
  • A successful resource creation commonly returns 201 Created.
  • The server should validate POST data before storing it.
  • A missing resource commonly results in 404 Not Found.
  • The frontend and backend communicate through HTTP requests and responses.
