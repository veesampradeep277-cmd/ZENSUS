Common API Authentication Methods

API KEY

API Key Authentication

A client receives a key and sends it with API requests.

BASIC AUTH

Basic Authentication

A username and password are sent using the HTTP Authorization header.

In modern applications, token-based authentication is common, especially when separate frontend and backend applications communicate through APIs.
04

API Key Authentication

An API key is a value issued to a client or application. The client sends the key with API requests so the server can identify the calling application.

Example

Request Header 
GET /weather/

X-API-Key: your_api_key_here

The server receives the key and checks whether it is valid.

Client
→
API Key
→
API Server
→
Verify Key
→
Response
Important:

An API key should be treated as a secret credential when the provider uses it for authenticated access. Do not publish private keys in frontend source code or public repositories.
05

Basic Authentication

HTTP Basic Authentication uses a username and password in the Authorization header.

Request

Basic Authentication 
GET /profile/

Authorization: Basic base64(username:password)

The credentials are represented using Base64 encoding.

Base64 is encoding, not encryption.

Basic Authentication should therefore be used with HTTPS/TLS so credentials are protected while being transmitted.

Important Concept

The server decodes the credentials, verifies the username and password, and then decides whether to process the request.

06

Bearer Token Authentication

A bearer token is an access credential. The client sends it in the Authorization header.

Request

Bearer Token 
GET /profile/

Authorization: Bearer eyJhbGciOi...
Authorization Token

The server validates the token before allowing access to the protected resource.

Basic Structure

Authorization Header 
Authorization: Bearer <access-token>
The word Bearer indicates that the client is presenting a bearer access token as the credential for the request.
07

JWT Authentication

JWT stands for JSON Web Token. It is a standardized token format frequently used in token-based authentication systems.

JWT Structure

JWT 
HEADER.PAYLOAD.SIGNATURE
1️⃣

Header

Contains metadata such as the signing algorithm and token type.

2️⃣

Payload

Contains claims such as a subject, issuer, expiration or user identifier depending on the application.

3️⃣

Signature

Allows the server to verify that the token was signed correctly and has not been altered.

Example JWT Shape

Illustration 
eyJhbGciOiJIUzI1NiJ9.
eyJzdWIiOiIxMDEiLCJleHAiOjE3MDAwMDB9.
signature_here
Do not put sensitive secrets inside a JWT payload just because the payload is encoded.

JWT payload data is typically readable by anyone who obtains the token. The signature provides integrity verification; it does not make ordinary JWT contents secret.

A common token-based flow works like this:

1
User logs in

The client sends login credentials to the authentication endpoint.

2
Server verifies credentials

The server checks the submitted credentials according to the application's authentication system.

3
Server issues a token

If authentication succeeds, the server provides an access token or another supported credential.

4
Client stores the credential safely

The application follows an appropriate storage strategy based on its platform and security requirements.

5
Client calls protected API

The access token is included with the request.

6
Server validates credential

The API checks whether the credential is valid, active and appropriate for the request.

7
Authorization is checked

The server determines whether this identity has permission to perform the requested operation.

8
Response is returned

The API returns the requested data or an appropriate error.

Roles & Permissions

A role is a category of access assigned to a user. Permissions define the actions that role or user is allowed to perform.

Student

  • View own profile
  • View courses
  • Submit assignments
  • Cannot manage users

Teacher

  • View students
  • Create course content
  • Update assignments
  • Manage selected student data

Admin

  • Manage users
  • Manage courses
  • Manage permissions
  • Access administrative endpoints

API Client

  • Access allowed endpoints
  • Use assigned credentials
  • Follow API rate limits
  • Cannot automatically access everything

Authorization Header

The Authorization header is commonly used to send authentication credentials to an API.

Bearer Token

HTTP Request 
GET /profile/ HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

Why Headers?

  • They separate authentication metadata from the resource URL.
  • They can be automatically added by HTTP clients.
  • They provide a standard place for authorization credentials.
  • They work naturally with frontend and backend API communication.
Always use HTTPS/TLS for production authenticated APIs.

Without secure transport, credentials or tokens may be exposed during network transmission.

Authentication & Authorization Errors

Status Meaning Typical Situation
401 Unauthorized Missing, invalid or expired authentication credentials
403 Forbidden Requester is authenticated but not allowed to perform action
404 Not Found Resource does not exist, or an API may intentionally hide its existence
429 Too Many Requests Rate limit exceeded

401 Example

Missing Token 
HTTP/1.1 401 Unauthorized

{
    "error": "Authentication required"
}

403 Example

Insufficient Permission 
HTTP/1.1 403 Forbidden

{
    "error": "You do not have permission to perform this action"
}
Remember:

401 generally relates to authentication.
403 generally relates to authorization.

API Authentication Security Best Practices

🔒 Use HTTPS

Use TLS/HTTPS so credentials and tokens are protected in transit.

🗝️ Protect Secrets

Never expose private API keys, signing secrets or passwords in public source code.

⏱️ Token Expiration

Use appropriate expiration policies for access credentials.

🚫 Enforce Permissions Server-Side

Never depend only on frontend controls for authorization.

📉 Rate Limiting

Limit excessive requests where appropriate to reduce abuse and protect resources.

🧹 Validate Input

Authentication does not replace validation. API input must still be validated and handled safely.

Never put secrets directly into frontend JavaScript.

Anything delivered to a browser can potentially be inspected by the user. Server-only secrets must remain on trusted backend systems.

Environment Variables

Example 
API_SECRET_KEY=your-secret-value
JWT_SECRET=your-secret-value
DATABASE_PASSWORD=your-password

The exact mechanism for loading environment variables depends on the backend technology being used.

Lesson Takeaway

  • Authentication verifies identity.
  • Authorization determines permissions.
  • APIs can use API keys, Basic Authentication, bearer tokens and other authentication mechanisms.
  • Bearer tokens are commonly sent using the Authorization header.
  • JWT is a standardized token format commonly used in token-based authentication systems.
  • JWT has three conceptual parts: Header, Payload and Signature.
  • A protected API should validate credentials before returning or changing protected data.
  • Roles and permissions can be used to implement authorization rules.
  • 401 commonly indicates an authentication problem.
  • 403 commonly indicates insufficient permission.
  • HTTPS/TLS should be used to protect credentials and tokens in transit.
  • Private secrets should remain on trusted server-side systems.
  • Frontend restrictions alone are not sufficient for authorization. The backend must enforce access control.
