HTTP Responses & Status Codes

Learn how servers respond to HTTP requests, understand response structure, master status-code categories, and learn how REST APIs communicate success and errors.

01

What is an HTTP Response?

An HTTP response is the message sent by a server back to the client after processing an HTTP request.

Client
→
HTTP Request
→
Server
→
HTTP Response
Simple definition:

An HTTP response tells the client what happened after the server received and processed the request.
02

HTTP Response Structure

An HTTP response contains several important parts.

🔢

Status Code

Indicates the result of the request.

Example: 200

📝

Status Message

A short description associated with the status.

Example: OK

📋

Headers

Metadata about the response.

📦

Body

Data returned to the client when applicable.

Example HTTP Response 
HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 101,
    "name": "Pradeep",
    "course": "REST API"
}
03

What are HTTP Status Codes?

An HTTP status code is a three-digit number returned by a server to describe the result of an HTTP request.

1xx

Informational

The request has been received and processing continues.

2xx

Success

The request was successfully received and processed.

3xx

Redirection

The client needs to take additional action or the resource has another location.

4xx

Client Error

Something about the request prevents it from being successfully processed.

5xx

Server Error

The server failed to successfully process a valid-looking request.

Easy memory trick:

1xx → Information
2xx → Success
3xx → Redirection
4xx → Client-side problem
5xx → Server-side problem
04

1xx — Informational Responses

The 1xx range represents informational responses. They indicate that the request has been received and processing can continue.

100

Continue

The initial part of the request has been received and the client can continue sending the request.

101

Switching Protocols

The server is switching to another protocol as requested by the client.

In everyday REST API development, you will work much more frequently with 2xx, 4xx and 5xx responses.
05

2xx — Successful Responses

The 2xx range indicates that the request was successfully received, understood and processed.

200

OK

The request succeeded.

201

Created

A new resource was successfully created.

202

Accepted

The request has been accepted for processing, but processing may not have completed yet.

204

No Content

The request succeeded and there is no response content to return.

Operation Common Status Meaning
GET successful 200 Resource returned
POST successful 201 Resource created
DELETE successful 204 Successful with no response body
06

3xx — Redirection Responses

The 3xx range indicates that additional action may be required to complete the request or that a resource has another location.

301

Moved Permanently

The resource has a permanent new location.

302

Found

The resource is temporarily available at another location.

304

Not Modified

The cached representation can still be used when appropriate.

REST API clients may encounter redirection responses, although many APIs are designed so normal API calls do not require the client to handle redirects frequently.
07

4xx — Client Error Responses

The 4xx range generally indicates that the request cannot be successfully processed because of something about the request or the client's authorization.

400

Bad Request

The server cannot process the request because it is invalid or malformed.

401

Unauthorized

The request lacks valid authentication credentials.

403

Forbidden

The server understood the request but refuses to authorize the requested action.

404

Not Found

The requested resource could not be found.

405

Method Not Allowed

The HTTP method is not supported for that resource.

409

Conflict

The request conflicts with the current state of the resource.

422

Unprocessable Content

The request format may be understood, but the submitted content fails application-level validation.

429

Too Many Requests

The client has sent too many requests in a given period.

08

5xx — Server Error Responses

The 5xx range indicates that the server failed to successfully fulfill an apparently valid request.

500

Internal Server Error

A generic unexpected server-side error occurred.

501

Not Implemented

The server does not support the functionality required to fulfill the request.

502

Bad Gateway

A gateway or proxy received an invalid response from an upstream server.

503

Service Unavailable

The server is currently unable to handle the request, often temporarily.

504

Gateway Timeout

A gateway or proxy did not receive a timely response from an upstream server.

10

Response Headers

Response headers provide metadata about the server response.

Content-Type

Tells the client what type of content is being returned.

application/json

Content-Length

Indicates the size of the response body when provided.

Cache-Control

Provides caching instructions.

Location

Can identify another URI, commonly with certain redirect or resource-creation responses.

Response Headers Example 
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache
11

Response Body

The response body contains the actual data returned by the server, when a body is appropriate for that response.

Student Response 
{
    "id": 101,
    "name": "Pradeep",
    "email": "pradeep@example.com",
    "course": "REST API",
    "active": true
}

The frontend can read this data and display it to the user.

Server
→
JSON
→
Frontend
→
UI
A successful response does not always need a response body. For example, 204 No Content indicates success without response content.
12

JSON API Responses

REST APIs commonly use JSON because it is lightweight and easy for many programming languages to process.

Successful JSON Response 
{
    "success": true,
    "message": "Student found",
    "data": {
        "id": 101,
        "name": "Pradeep",
        "course": "REST API"
    }
}

A consistent response structure can make frontend development easier.

Good API practice:

Keep your response structure predictable and document what clients should expect.
13

Error Responses

When something goes wrong, a useful API should provide a meaningful status code and enough structured information for the client to understand the problem.

404 Example 
HTTP/1.1 404 Not Found
Content-Type: application/json

{
    "error": "Student not found",
    "code": "STUDENT_NOT_FOUND"
}
Validation Error Example 
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
    "error": "Invalid student data",
    "fields": {
        "email": "Enter a valid email address."
    }
}
Important:

Do not expose sensitive internal information such as database passwords, secret keys, stack traces or private infrastructure details in API error responses.

Lesson Takeaway

  • An HTTP response is sent by the server after processing a request.
  • A response can contain a status code, headers and a body.
  • 1xx codes are informational.
  • 2xx codes indicate success.
  • 3xx codes indicate redirection or additional action.
  • 4xx codes generally indicate a problem with the request or authorization.
  • 5xx codes indicate server-side failures.
  • 200 means the request succeeded.
  • 201 commonly means a resource was created.
  • 204 means the operation succeeded without response content.
  • 400 commonly indicates an invalid request.
  • 401 relates to missing or invalid authentication credentials.
  • 403 means access is not permitted.
  • 404 means the requested resource was not found.
  • 429 means the client has sent too many requests.
  • 500 indicates an unexpected server-side failure.
