1. Frontend Security

Frontend security is the practice of reducing security risks in the browser-based part of an application.

React provides useful defaults that reduce some common injection risks, but React itself cannot make an entire application secure. Security also depends on the backend, authentication system, browser configuration, dependencies and deployment environment.

2. XSS — Cross-Site Scripting

Cross-Site Scripting, commonly called XSS, occurs when attacker-controlled content is interpreted as executable code in another user's browser.

Conceptual Attack Flow

1 Attacker creates malicious input
2 Application handles it incorrectly
3 Content reaches browser
4 Browser interprets dangerous content
5 User is affected

Why React Helps

React normally escapes values inserted into JSX text and attribute values. This means ordinary rendering is safer than directly constructing HTML.

Safe rendering 
function Message({ message }) {
    return (
        <p>
            {message}
        </p>
    );
}

If message contains markup-like text, React treats it as data rather than automatically interpreting it as HTML.

React's default escaping is helpful, but developers can still introduce security problems through unsafe APIs, third-party libraries, server responses or incorrect handling of untrusted data.

Common XSS Categories

Type Concept
Stored XSS Malicious content is stored by an application and later displayed.
Reflected XSS Malicious input is reflected through an application response.
DOM-based XSS Client-side JavaScript creates a dangerous DOM interpretation.

3. Input Handling

User input should always be considered untrusted.

→

→

→

Client Validation

validation.js 
function validateUsername(username) {

    const value = username.trim();

    if (value.length < 3) {
        return "Username is too short";
    }

    return null;
}
Client-side validation improves user experience. It is NOT a replacement for server-side validation because users can bypass frontend code.

Security Rules

  • Validate data on the server.
  • Use allowlists where practical.
  • Enforce length limits.
  • Validate expected formats.
  • Do not trust hidden form fields.
  • Do not assume client-side restrictions cannot be bypassed.

4. Dangerous HTML

React provides an API called dangerouslySetInnerHTML for inserting raw HTML into the DOM.

Dangerous HTML 
function Article({ html }) {
    return (
        <div
            dangerouslySetInnerHTML={{
                __html: html
            }}
        />
    );
}
The name is intentional. Never place arbitrary untrusted HTML into dangerouslySetInnerHTML without an appropriate sanitization strategy.

Safer Pattern

Risky

Untrusted HTML

↓

Direct HTML injection

↓

Potential XSS

Safer

Untrusted content

↓

Validate / sanitize according to context

↓

Render intentionally

HTML sanitization is context-sensitive. Do not assume that a simple string replacement is a complete security solution.

5. Authentication Security

Authentication answers: “Who are you?”

Authorization answers: “What are you allowed to do?”

1

Authentication

Verifies identity using credentials, sessions, tokens or other authentication mechanisms.

2

Authorization

Determines whether an authenticated user has permission to perform an operation.

Login Architecture

Login Form
→
HTTPS
→
Authentication API
→
Session
→
Protected API

Important Rules

  • Never send passwords over an unencrypted connection.
  • Passwords should be handled by a properly designed backend authentication system.
  • Use strong authentication practices on the server.
  • Perform authorization checks on the server.
  • Do not rely on hiding a button as authorization.
A React condition such as user.role === "admin" can control what the UI displays, but it must never be the only protection for an admin API endpoint.

6. Token Security

Many applications use access tokens or other credentials to represent an authenticated session.

Token Flow

Login User authenticates
Issue Server establishes session/credential
Store Browser handles credential
Send Credential accompanies authorized requests
Verify Server checks authorization

Storage Considerations

Storage Security Consideration
localStorage Accessible to JavaScript; XSS can expose stored credentials.
sessionStorage Also accessible to JavaScript; lifetime is tied to the tab/session behavior.
HttpOnly Cookie JavaScript cannot directly read the cookie.
There is no universal storage choice that automatically solves all authentication security problems. Session design, cookie attributes, CSRF protection, XSS prevention, expiration and backend controls all matter.

Do Not Put Secrets in React Source

Never do this 
const SECRET_KEY =
    "super-secret-production-key";

Frontend JavaScript is delivered to the user's browser. A value embedded in frontend code should be considered potentially visible.

7. Cookies

Cookies allow browsers to store small pieces of data associated with a website or domain.

Important Cookie Attributes

Attribute Purpose
HttpOnly Prevents JavaScript from reading the cookie through document.cookie.
Secure Instructs the browser to send the cookie only over secure connections.
SameSite Controls when cookies are sent in cross-site contexts.
Expires / Max-Age Controls cookie lifetime.

Example Concept

Server-side concept 
Set-Cookie:
session=VALUE;
HttpOnly;
Secure;
SameSite=Lax
Cookie configuration should match the application's architecture. For cross-site authentication flows, SameSite and CSRF protections need careful consideration.

8. CSRF Concepts

CSRF stands for Cross-Site Request Forgery. It is a class of attack in which a victim's browser is induced to send an unwanted authenticated request to a site where the victim is already authenticated.

Conceptual Flow

Victim
Browser
→
Malicious
Site
→
Authenticated
Request
→
Target
Server

Common Defenses

SameSite Cookies

Restrict when cookies are sent in cross-site requests.

CSRF Tokens

Require an unpredictable token associated with the user's session.

Origin Checks

Servers can validate relevant request origin information.

CSRF protection depends on how authentication works. Cookie-based authentication requires particular attention to CSRF. Bearer-token architectures have different considerations.

9. CORS

CORS means Cross-Origin Resource Sharing. It is a browser security mechanism that controls whether frontend JavaScript can access resources from another origin.

What Is an Origin?

An origin is determined by the combination of:

  • Scheme
  • Host
  • Port
React App
Origin A
→
Browser
→
API
Origin B

Example Backend Configuration

Express concept 
import cors from "cors";

app.use(cors({
    origin: "https://example.com"
}));
CORS is not an authentication system. It controls browser cross-origin access; it does not replace authorization on the server.

Important Distinction

Concept Purpose
CORS Browser cross-origin access control.
Authentication Establishes identity.
Authorization Controls permissions.
CSRF Protection Defends against unwanted authenticated requests in relevant architectures.

10. Environment Variables

Environment variables are commonly used to configure applications differently across development, testing and production.

React/Vite Example

.env 
VITE_API_URL=https://api.example.com
React 
const apiUrl =
    import.meta.env.VITE_API_URL;
In Vite applications, variables exposed through the frontend build are available to client-side code. They are configuration values, not a secure vault for private server secrets.

11. Sensitive Information

Sensitive information should not be unnecessarily exposed to the browser, source code, logs or client-side storage.

Examples

!

Passwords

Never expose or log user passwords.

!

Private Keys

Keep server-side cryptographic secrets private.

!

Database Credentials

Database credentials belong on the server.

!

Access Tokens

Protect authentication credentials and minimize their lifetime where appropriate.

!

Personal Data

Collect and expose only what the application needs.

!

Internal Errors

Do not expose unnecessary server internals to users.

Bad Error Handling

Avoid 
catch (error) {
    setMessage(error.stack);
}

Better User Experience

Safer UI message 
catch (error) {
    setMessage(
        "Something went wrong. Please try again."
    );
}
Detailed technical errors can be logged securely on the server or sent to an approved monitoring system without exposing unnecessary internals to the end user.

Security Practices

  • Keep dependencies reasonably up to date.
  • Review security advisories.
  • Remove packages that are no longer needed.
  • Review unfamiliar dependencies before installing them.
  • Use lockfiles for reproducible installations.
  • Run package-manager security auditing tools.
  • Review dependency changes during code review.

Example Commands

Terminal

A vulnerability report does not automatically mean your application is exploitable. Review the affected package, version, dependency path, runtime usage and available fixes before deciding how to respond.

13. Secure API Communication

React applications frequently communicate with backend APIs. The browser-to-server boundary is one of the most important security boundaries in a full-stack application.

Secure Communication Flow

1 User action
2 HTTPS request
3 Authentication
4 Authorization
5 Validated response

Frontend Request

api.js 
async function getProfile() {

    const response = await fetch(
        `${import.meta.env.VITE_API_URL}/profile`,
        {
            credentials: "include"
        }
    );

    if (!response.ok) {
        throw new Error("Request failed");
    }

    return response.json();
}

Backend Must Still Verify

  • Authentication
  • Authorization
  • Input validation
  • Resource ownership
  • Rate limits where appropriate
  • Business rules
  • Safe error responses
Never assume that because a React button is hidden or disabled, the corresponding API operation is protected. The server must enforce authorization.

15. Quick Quiz

Check your understanding of React security fundamentals.

Q1. What is XSS?

Cross-Site Scripting is a class of attacks involving attacker-controlled content being interpreted as executable code in another user's browser.

Q2. Why should client-side validation not be treated as security?

Because users can bypass or modify frontend code. Important validation and authorization must be enforced on the server.

Q3. Why is dangerouslySetInnerHTML risky?

It inserts raw HTML into the DOM, so unsafe untrusted HTML can create XSS risk if it is not handled with an appropriate sanitization strategy.

Q4. Which cookie attribute prevents JavaScript from reading the cookie?

HttpOnly.

Q5. What does CORS primarily control?

It controls whether browser JavaScript is permitted to access resources across origins under the browser's CORS rules.

Q6. Can a VITE_ environment variable be used as a private secret?

No. Frontend-exposed environment variables become part of the client application and should not contain private server secrets.

Q7. Where should authorization ultimately be enforced?

On the server/API that protects the resource or operation.

Q8. What is CSRF?

Cross-Site Request Forgery is a class of attacks involving unwanted authenticated requests sent to a target site from a victim's browser.
