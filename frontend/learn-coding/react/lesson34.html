01 • CODE SPLITTING

What is Code Splitting?

Code splitting means dividing your application's JavaScript into smaller chunks instead of sending the entire application to the browser during the initial page load.

Traditional Bundle

The browser downloads a large JavaScript bundle containing code for every page and feature.

Initial JavaScript Large

Code-Split Application

Only the code required for the current screen is loaded initially. Other chunks can be downloaded later.

Initial JavaScript Smaller
Application React source
→
Build Tool Vite / Webpack
→
JavaScript Chunks Multiple files
→
Browser Loads when needed
Important: Code splitting does not magically make your application code faster. It changes when code is downloaded and evaluated, which can reduce the amount of JavaScript needed during the initial load.
02 • DYNAMIC IMPORTS

Dynamic Imports

JavaScript normally uses static imports that are loaded as part of the module graph. A dynamic import allows a module to be requested asynchronously when execution reaches that point.

Static Import

JavaScript
import Dashboard from "./Dashboard";

The module becomes part of the application's normal module dependency graph.

Dynamic Import

JavaScript
const module = await import("./Dashboard");

The module can be loaded asynchronously when required.

Dynamic Import Flow

User Action Click / Route
→
import() Request chunk
→
Network Download module
→
Module Execute code
Dynamic imports are one of the mechanisms that make practical code splitting possible.
03 • REACT.LAZY()

React.lazy()

React.lazy() lets you render a component that is loaded dynamically. The component is represented by a lazy component until its module has been loaded.

React
import { lazy } from "react";

const Dashboard = lazy(
    () => import("./Dashboard")
);

What happens?

  • React encounters the lazy component.
  • The import function starts loading the module.
  • The module is downloaded asynchronously.
  • React waits for the lazy component.
  • The component renders after loading completes.

Why use it?

  • Reduce initial JavaScript.
  • Delay rarely needed features.
  • Split large applications.
  • Load route components on demand.
  • Improve initial loading experience.
A lazy component needs an appropriate Suspense boundary above it. Without a boundary that can handle the suspended rendering, the UI cannot provide the intended loading experience.
04 • SUSPENSE

What is Suspense?

Suspense provides a declarative way to specify what React should display while part of the UI is not yet ready to render.

React
import { Suspense } from "react";

<Suspense fallback={<Loading />}>

    <Dashboard />

</Suspense>
Suspense Rendering Model
Suspense Boundary
→
Content Ready Render children
or
Content Waiting Render fallback
Suspense itself is not a network library and it does not perform arbitrary data fetching by itself. In this lesson, the common use case is handling lazy-loaded React components.
05 • FALLBACK UI

Fallback UI

A fallback is the temporary interface displayed while the suspended content is waiting to become available.

Simple Spinner

Loading Dots

React
function Loading() {
    return (
        <div className="loading">
            Loading dashboard...
        </div>
    );
}

<Suspense fallback={<Loading />}>
    <Dashboard />
</Suspense>

Good Fallback UI

Fast

The fallback should appear immediately instead of making the user stare at an empty screen.

Contextual

A dashboard skeleton can be more useful than a generic full-screen spinner when only part of the page is loading.

Stable

Avoid layouts that dramatically jump when the real component appears.

Accessible

Loading indicators should communicate that content is currently being prepared.

06 • ROUTE-LEVEL LOADING

Route-Level Lazy Loading

Large applications commonly split code by page or route. Users do not necessarily need the JavaScript for every page during the first visit.

Route-Based Code Splitting
App Initial bundle
→
Home Chunk Loaded first
+
Dashboard Chunk Loaded later
+
Settings Chunk Loaded later
React Router Pattern
import { lazy, Suspense } from "react";

const Home = lazy(() => import("./pages/Home"));
const Dashboard = lazy(() => import("./pages/Dashboard"));
const Settings = lazy(() => import("./pages/Settings"));

function App() {

    return (
        <Suspense fallback={<PageLoader />}>

            <Routes>

                <Route
                    path="/"
                    element={<Home />}
                />

                <Route
                    path="/dashboard"
                    element={<Dashboard />}
                />

                <Route
                    path="/settings"
                    element={<Settings />}
                />

            </Routes>

        </Suspense>
    );
}
This approach can prevent every page's JavaScript from being required before the user even visits that page.
07 • COMPONENT-LEVEL LOADING

Component-Level Lazy Loading

Code splitting does not have to happen only at the route level. A large feature inside a page can also be loaded only when needed.

Example Features

  • Analytics dashboard
  • Chart library
  • Rich text editor
  • Advanced code editor
  • Admin tools
  • Large visualization

Lazy Component

const Analytics =
    lazy(() => import("./Analytics"));

function Dashboard() {

    return (
        <Suspense
            fallback={<ChartLoader />}
        >

            <Analytics />

        </Suspense>
    );
}
Use component-level splitting when a feature is relatively expensive or unlikely to be needed immediately. Splitting every tiny component can create unnecessary complexity and additional network requests.
08 • LOADING BOUNDARIES

Loading Boundaries

A Suspense boundary controls which portion of the interface can show a fallback while its suspended children are waiting.

One Large Boundary

<Suspense fallback={<FullPageLoader />}>

    <Header />
    <Sidebar />
    <Dashboard />
    <Recommendations />

</Suspense>

Multiple Smaller Boundaries

<Header />

<Suspense fallback={<DashboardSkeleton />}>
    <Dashboard />
</Suspense>

<Suspense fallback={<RecommendationSkeleton />}>
    <Recommendations />
</Suspense>

Coarse Boundary

Simple architecture. Useful when a whole section naturally belongs together during loading.

Fine-Grained Boundaries

Different parts of the interface can reveal themselves independently, creating a more progressive experience.

More boundaries are not automatically better. Choose boundaries around meaningful UI sections rather than creating one around every component.
09 • PERFORMANCE BENEFITS

Why Lazy Loading Can Help Performance

1. Smaller Initial Download

Users may download less JavaScript during the initial page load.

2. Less Initial Parsing

The browser does not need to parse and evaluate every deferred chunk immediately.

3. Faster Feature Discovery

Important application features can become available without requiring every optional feature first.

4. Better Scalability

Large applications can divide their JavaScript into meaningful chunks.

Initial Request Small core
→
Render Important UI
→
User navigates New feature
→
Load Chunk On demand
Performance improvement depends on the application, network, device, chunk sizes and loading strategy. Always measure real applications rather than assuming that more chunks automatically means better performance.

Complete Lazy Dashboard Example

Imagine a student platform such as ZENSUS. The home page is frequently visited, while Analytics and Admin tools may be used by only a smaller portion of users.

Step 1 — Create Components

export default function Home() {

// Admin.jsx

export default function Admin() {
    return (
        <section>
            <h2>Admin Panel</h2>

        </section>

}

Step 2 — Lazy Load Features

import { lazy, Suspense } from "react";

const Home =
    lazy(() => import("./Home"));

const Analytics =
    lazy(() => import("./Analytics"));

const Admin =
    lazy(() => import("./Admin"));

Step 3 — Create a Loading Component

function PageLoader() {

    return (
        <div className="page-loader">
            Loading page...
        </div>
    );
}

function App() {

    return (
        <Suspense fallback={<PageLoader />}>

            <Home />
            <Analytics />

    );
}

11 • COMMON MISTAKES

Common Suspense & Lazy Loading Mistakes

❌ Lazy Loading Everything

Creating a separate chunk for every tiny component can add complexity without meaningful performance benefits.

❌ Poor Fallback UI

A giant spinner replacing the entire page can create a poor experience when only one small section is loading.

❌ Forgetting Suspense

A lazy component needs an appropriate Suspense boundary to handle its suspended rendering.

❌ Huge Lazy Chunks

A lazy-loaded chunk can still be too large. Splitting code does not automatically make each chunk small.

❌ Assuming More Chunks = Faster

Excessive splitting can introduce additional loading overhead and complexity.

❌ Ignoring Measurement

Use performance tools and production-like testing to determine whether the loading strategy actually helps.

Remember: The goal is not “maximum lazy loading.” The goal is delivering the right amount of code at the right time while maintaining a good user experience.
12 • QUICK REFERENCE

Suspense & Lazy Loading Cheat Sheet

  • Code Splitting: Break application JavaScript into independently loadable chunks.
  • Dynamic Import: Use import() to load a module asynchronously.
  • React.lazy(): Create a component whose module is loaded dynamically.
  • Suspense: Define fallback UI for suspended rendering.
  • Fallback: Temporary UI displayed while content is waiting.
  • Route-Level Loading: Split application code by page or route.
  • Component-Level Loading: Split expensive or optional features within a page.
  • Loading Boundary: Controls which UI region is replaced by a fallback.
  • Performance: Reduce initial JavaScript and defer non-critical code.
