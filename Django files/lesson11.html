Class-Based Views & Middleware

Learn how Django uses classes to organize reusable view logic and how middleware can inspect or modify requests and responses as they travel through the Django application.

01

What are Class-Based Views?

A Class-Based View, or CBV, is a Django view written using a Python class instead of a simple function.

In earlier lessons, we used Function-Based Views: 

from django.http import HttpResponse

def home(request):
    return HttpResponse("Welcome to ZENSUS!")

The same idea can be written as a class: 

from django.views import View
from django.http import HttpResponse

class HomeView(View):

    def get(self, request):
        return HttpResponse("Welcome to ZENSUS!")
Core idea: A CBV organizes related request-handling behavior inside a class.
02

Why Use Class-Based Views?

01

Reusable Logic

Common behavior can be placed in reusable classes.

02

Organized Code

GET, POST and other HTTP methods can be separated clearly.

03

Inheritance

One class can inherit functionality from another class.

04

Generic Views

Django provides ready-made generic CBVs for common operations.

Think of it this way

Function View
One function
→

Organized behavior
→
Generic View
Reusable Django logic
03

Function-Based View vs Class-Based View

Function-Based View

def home(request):

    if request.method == "GET":
        return HttpResponse(
            "Home Page"
        )

Simple and beginner-friendly. Excellent when the logic is small and straightforward.

Class-Based View

class HomeView(View):

    def get(self, request):
        return HttpResponse(
            "Home Page"
        )

Useful when related behaviors need to be organized and reused.

Important: CBVs are not automatically "better" than FBVs. Choose the approach that keeps the application understandable and maintainable.

06

Handling GET and POST

One major advantage of CBVs is that different HTTP methods can be placed into different methods. 

from django.views import View
from django.http import HttpResponse

class StudentView(View):

    def get(self, request):

        return HttpResponse(
            "Student Form"
        )

    def post(self, request):

        name = request.POST.get("name")

        return HttpResponse(
            f"Student: {name}"
        )
GET

get()

Usually used to display a page or retrieve information.

POST

post()

Usually used when submitting data to the server.

In a real HTML form that sends POST data, include Django's {% csrf_token %} inside the form.

ListView and DetailView

Example Model

class Student(models.Model):

    name = models.CharField(
        max_length=100
    )

    course = models.CharField(
        max_length=100
    )

ListView

from django.views.generic import ListView
from .models import Student

class StudentListView(ListView):

    model = Student
    template_name = "students.html"
    context_object_name = "students"

DetailView

from django.views.generic import DetailView
from .models import Student

class StudentDetailView(DetailView):

    model = Student
    template_name = "student_detail.html"
    context_object_name = "student"

URLs

from django.urls import path
from .views import (
    StudentListView,
    StudentDetailView
)

urlpatterns = [

    path(
        "students/",
        StudentListView.as_view(),
        name="student-list"
    ),

    path(
        "student//",
        StudentDetailView.as_view(),
        name="student-detail"
    ),

]

CreateView and UpdateView

Generic editing views can significantly reduce repetitive CRUD code.

CreateView

from django.urls import reverse_lazy
from django.views.generic import CreateView

class StudentCreateView(CreateView):

    model = Student

    fields = [
        "name",
        "course"
    ]

    template_name = "student_form.html"

    success_url = reverse_lazy(
        "student-list"
    )

UpdateView

from django.views.generic import UpdateView

class StudentUpdateView(UpdateView):

    model = Student

    fields = [
        "name",
        "course"
    ]

    template_name = "student_form.html"

    success_url = reverse_lazy(
        "student-list"
    )
Big advantage: Django handles much of the repetitive form-processing logic for these generic views.

What is Middleware?

Middleware is a layer that sits between the incoming request and the Django view, and also between the view's response and the browser.

Django Built-in Middleware

Django projects normally include several middleware components in settings.py. 

MIDDLEWARE = [

    "django.middleware.security.SecurityMiddleware",

    "django.contrib.sessions.middleware.SessionMiddleware",

    "django.middleware.common.CommonMiddleware",

    "django.middleware.csrf.CsrfViewMiddleware",

    "django.contrib.auth.middleware.AuthenticationMiddleware",

    "django.contrib.messages.middleware.MessageMiddleware",

    "django.middleware.clickjacking.XFrameOptionsMiddleware",

]
Middleware Purpose
SecurityMiddleware Provides several security-related protections.
SessionMiddleware Enables session support.
CommonMiddleware Provides common request/response processing.
CsrfViewMiddleware Helps protect against CSRF attacks.
AuthenticationMiddleware Adds the authenticated user to request.user.
MessageMiddleware Supports Django's messaging framework.
13

Creating Custom Middleware

You can create your own middleware when application-wide request or response processing is required.

Step 1 — Create middleware.py

products/ │ ├── middleware.py ├── models.py ├── views.py ├── urls.py └── admin.py

Step 2 — Write Middleware

class SimpleMiddleware:

    def __init__(self, get_response):

        self.get_response = get_response

    def __call__(self, request):

        print("Before View")

        response = self.get_response(request)

        print("After View")

        return response

Step 3 — Register It

MIDDLEWARE = [

    "products.middleware.SimpleMiddleware",

    "django.middleware.security.SecurityMiddleware",

    "django.contrib.sessions.middleware.SessionMiddleware",

    # ...

]
Important: Middleware order can matter because middleware components can wrap and influence one another.
14

Authentication Middleware

One important built-in middleware is AuthenticationMiddleware. 

"django.contrib.auth.middleware.AuthenticationMiddleware"

It works with Django's authentication system and makes the current authenticated user available through: 

request.user

Example

from django.http import HttpResponse

def dashboard(request):

    if request.user.is_authenticated:

        return HttpResponse(
            f"Welcome {request.user.username}"
        )

    return HttpResponse(
        "Please login"
    )
This connects directly with Lesson 09: Authentication & Authorization.

Common Mistakes

01

Forgetting as_view()

CBVs normally need MyView.as_view() in URL patterns.

02

Wrong HTTP Method

GET requests are handled by get(), POST requests by post().

03

Wrong Generic View

Choose ListView, DetailView, CreateView, UpdateView or another appropriate generic view.

04

Middleware Not Registered

Custom middleware must be added to MIDDLEWARE in settings.py.

05

Wrong Middleware Order

Some middleware depends on other middleware being available earlier.

06

Too Much Abstraction

Do not use complex CBVs or middleware when a simple view is clearer.

Beginner rule: First understand Function-Based Views clearly. Then learn CBVs as another way to organize view logic.

Lesson Takeaway

  • Class-Based Views represent Django views using Python classes.
  • HTTP methods such as GET and POST can be handled separately.
  • CBVs are connected to URLs using as_view().
  • Django provides generic views for common patterns.
  • ListView displays collections of objects.
  • DetailView displays one object's details.
  • CreateView and UpdateView simplify form-based CRUD operations.
  • Middleware processes requests and responses around the view layer.
  • Django includes several built-in middleware components.
  • Custom middleware can be created for application-specific processing.
  • Middleware order can affect application behavior.
Core concept:

Browser Request → Middleware → URL → Class-Based View → Model / Template → Middleware → Browser Response
