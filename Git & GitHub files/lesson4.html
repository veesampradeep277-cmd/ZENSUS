LESSON 04 • BEGINNER

Git Status, Add & Commit

Learn how Git tracks file changes, how to inspect your repository using git status, how to move changes into the staging area with git add, and how to permanently record a project version using git commit.

git status git add Staging Area git commit Commit Messages
01 — Foundation

The Working Directory

The working directory is the actual project folder where you create, edit, and delete files.

For example, imagine a project containing:

Project Structure 
my-project/
│
├── index.html
├── style.css
└── script.js

When you modify one of these files, Git can detect that the working directory has changed.

Example: If you change the heading inside index.html, Git can detect that the file has been modified.

02 — Inspect

git status

git status shows the current state of your Git repository.

Terminal 
git status

It can tell you:

  • Which branch you are currently on
  • Whether files have been modified
  • Which files are untracked
  • Which files are staged
  • Whether there is anything to commit

Example: Clean Repository

Output 
On branch main

nothing to commit, working tree clean

This means Git currently sees no uncommitted changes.

Example: Modified File

Output 
On branch main

Changes not staged for commit:
  modified:   index.html

Git knows that index.html changed, but the change has not been staged yet.

Example: Untracked File

Output 
Untracked files:
  notes.txt

An untracked file is a new file that Git is not currently tracking in the repository.

03 — Core Concept

What Is the Staging Area?

The staging area is an intermediate area where you select the changes that should be included in the next commit.

Working Directory You edit files
→
Staging Area You select changes
→
Repository You commit changes

This gives you control over what goes into a commit.

Think of staging as preparing a package before sending it. You choose exactly what should be included in that package.

04 — Command

git add

The git add command moves selected changes into the staging area.

Add One File

Terminal 
git add index.html

This stages only index.html.

Add Multiple Specific Files

Terminal 
git add index.html style.css

This stages both files.

Add All Changes

Terminal 
git add .

The dot means to stage changes from the current directory according to Git's normal tracking and ignore rules.

Before using git add ., it is good practice to run git status and make sure you understand which files will be staged.

05 — Save a Version

git commit

A commit records a snapshot of the staged changes in the Git repository.

The basic command is:

Terminal 
git commit -m "Your commit message"

The -m option allows you to provide the commit message directly.

Example

Terminal 
git commit -m "Add homepage"

A commit is a recorded version of your project. Later, Git can use these commits to show history and help you compare versions.

06 — Best Practice

Writing Good Commit Messages

A commit message should briefly explain what the commit changed.

Good Message Weak Message
Add login form changes
Fix navigation bug update
Add student registration API done
Update homepage styling asdf

Useful Pattern

Examples 
Add ...
Fix ...
Update ...
Remove ...
Refactor ...

Your commit history should make sense when another developer reads it later.

07 — Practical Example

Adding a Single File

Suppose you created a new file:

Project 
about.html

Check the repository:

Command 
git status

Stage the file:

Command 
git add about.html

Check again:

Command 
git status

Finally, commit:

Command 
git commit -m "Add about page"
08 — Practical Example

Adding Multiple Files

Suppose you modified three files:

Modified Files 
index.html
style.css
script.js

You can stage them together:

Command 
git add index.html style.css script.js

Or stage the relevant changes from the current directory:

Command 
git add .

Then create a commit:

Command 
git commit -m "Update homepage"
09 — Core Workflow

Working Directory → Staging → Repository

1. Edit Change project files
→
2. git add Stage selected changes
→
3. git commit Record a version

This is one of the most important workflows to understand when learning Git.

Stage What happens? Main command
Working Directory You create or modify files. Edit files
Staging Area You select changes for the next commit. git add
Repository You record the staged changes. git commit
10 — First Commit

Creating Your First Commit

Suppose you have already initialized a repository and created index.html.

A typical first-commit sequence is:

First Commit Workflow 
git status

git add index.html

git status

git commit -m "Initial commit"

git status

What happens?

  1. git status checks the current state.
  2. git add moves the selected file to staging.
  3. The second git status confirms the file is staged.
  4. git commit records the staged changes.
  5. The final git status shows whether uncommitted changes remain.

After a successful commit, you may see: nothing to commit, working tree clean.

11 — Troubleshooting

Common Mistakes

01

Skipping git status

Beginners often stage or commit without checking what changed.

02

Forgetting git add

Changes must normally be staged before they can be included in a commit.

03

Empty Commit

If there are no staged changes, Git may report that there is nothing to commit.

04

Bad Commit Messages

Messages such as "update" make project history difficult to understand.

05

Staging the Wrong Files

Check the staged files before committing important work.

06

Thinking Commit = GitHub

A commit is stored locally until you push it to a remote repository.

Important: git commit does not automatically send your changes to GitHub. Uploading to a remote repository is covered later with git push.

Lesson Takeaway

  • git status shows the current state of your repository.
  • The working directory contains the files you are editing.
  • The staging area contains changes selected for the next commit.
  • git add filename stages a specific file.
  • git add . stages changes from the current directory according to Git's rules.
  • git commit records staged changes as a project version.
  • Good commit messages explain what changed.
  • A local commit is not automatically uploaded to GitHub.
