1. The Production Mindset

A production application should not assume that everything will always work correctly.

Development mindset:

"What happens when everything works?"


Production mindset:

"What happens when the network fails, the API returns an error, the database is unavailable, the user enters invalid information, or a component crashes?"

User Action
→
React Application
→
API Request
→
Failure Something goes wrong

Good error handling converts unexpected failures into controlled application states.

2. Runtime Errors

A runtime error occurs while JavaScript is executing.

Example

Runtime error 
function UserProfile() {

    const user = null;

    return (
        <h2>
            {user.name}
        </h2>
    );
}

Trying to access a property from a null value can cause an exception.

Safer approach

function UserProfile({ user }) {

    if (!user) {
        return <p>User not available</p>;
    }

    return (
        <h2>
            {user.name}
        </h2>
    );
}
Important principle:

Prevent predictable errors through validation and conditional rendering, but use error boundaries for unexpected rendering failures.

3. Error Boundaries

An Error Boundary is a React component designed to catch rendering errors in its child component tree and display fallback UI.

Component Failure Protection
App Application
→
Error Boundary Protection Layer
→
Broken Component Error
→
Fallback UI Safe screen

Class-based Error Boundary

import React from "react";

class ErrorBoundary extends React.Component {

    constructor(props) {

        super(props);

        this.state = {
            hasError: false
        };
    }

    static getDerivedStateFromError() {

        return {
            hasError: true
        };
    }

    componentDidCatch(error, info) {

        console.error(error, info);
    }

    render() {

        if (this.state.hasError) {

            return (
                <div>
                    <h2>
                        Something went wrong.
                    </h2>

                    <p>
                        Please try again later.
                    </p>
                </div>
            );
        }

        return this.props.children;
    }
}

export default ErrorBoundary;

Using the boundary

function App() {

    return (
        <ErrorBoundary>

            <Dashboard />

        </ErrorBoundary>
    );
}
What Error Boundaries are not:
  • They are not a replacement for try/catch around normal asynchronous API requests.
  • They do not mean every possible JavaScript error is automatically handled.
  • They should be combined with proper API and form error handling.

4. API Errors

Frontend applications communicate with servers, and servers can return success or failure responses.

API request handling 
async function loadUsers() {

    try {

        const response =
            await fetch("/api/users");

        if (!response.ok) {

            throw new Error(
                `Request failed: ${response.status}`
            );
        }

        const data =
            await response.json();

        return data;

    } catch (error) {

        console.error(error);

        throw error;
    }
}

Why response.ok matters

A fetch promise can resolve even when the server responds with an HTTP error status. The application should explicitly inspect the response.

5. HTTP Status Codes

200 OK

The request succeeded.

201 Created

A resource was successfully created.

204 No Content

The request succeeded without a response body.

400 Bad Request

The server could not process invalid request data.

401 Unauthorized

Authentication is required or failed.

403 Forbidden

The server refuses the requested operation.

404 Not Found

The requested resource could not be found.

500 Internal Server Error

The server encountered an unexpected problem.

503 Service Unavailable

The service is temporarily unable to handle the request.

6. Loading, Empty & Error States

A professional application should explicitly represent the state of an asynchronous operation.

...

Loading State

The request is currently running.

✓

Success State

Data was successfully loaded.

∅

Empty State

The request succeeded but there is no data.

!

Error State

The operation failed.

Typical state machine

Idle Nothing started
→
Loading Request running
→
Success Data available

The loading state can transition into either a successful result or an error. A successful request can also produce an empty result.

7. Fallback UI

Fallback UI is the interface displayed when the expected content cannot be rendered or loaded.

Good fallback

Something went wrong while loading the dashboard.

Bad fallback

Something went wrong.

No useful information or recovery action is provided.

Example

if (error) {

    return (
        <div className="error">

            <h2>
                Unable to load dashboard
            </h2>

            <p>
                Please check your connection
                and try again.
            </p>

            <button onClick={loadDashboard}>
                Try Again
            </button>

        </div>
    );
}

8. Form Errors

Form validation should tell users exactly what needs to be corrected.

Please enter a valid email address.
Password must satisfy the application's required rules.

React validation example

const [errors, setErrors] = useState({});


function validate(form) {

    const newErrors = {};

    if (!form.email) {

        newErrors.email =
            "Email is required";
    }

    if (!form.password) {

        newErrors.password =
            "Password is required";
    }

    setErrors(newErrors);

    return Object.keys(newErrors).length === 0;
}
Good validation message:

"Email is required."

Avoid:

"Invalid input."

9. Network Errors

Not every failure is caused by your React code. The user's network, server availability or connection can fail.

Offline

The device has no usable network connection.

Timeout

The request takes too long to complete.

Server Down

The backend cannot currently serve requests.

Basic handling

try {

    const response =
        await fetch("/api/products");

    if (!response.ok) {
        throw new Error(
            "Server request failed"
        );
    }

} catch (error) {

    setError(
        "Unable to connect to the server. "
        + "Please try again."
    );
}

10. Retry Logic

Temporary failures may succeed if the request is attempted again.

Request
→
Failure
→
Retry
→
Success

Simple retry function

async function fetchWithRetry(
    url,
    attempts = 3
) {

    for (
        let attempt = 1;
        attempt <= attempts;
        attempt++
    ) {

        try {

            const response =
                await fetch(url);

            if (!response.ok) {
                throw new Error(
                    "Request failed"
                );
            }

            return await response.json();

        } catch (error) {

            if (attempt === attempts) {
                throw error;
            }
        }
    }
}
Production consideration:

Retry logic should be designed carefully. Automatically retrying every failure can increase server load or repeat operations that should not be repeated. Retry behavior should depend on the type of request and failure.

11. User-Friendly Error Messages

Technical message

"TypeError: Failed to fetch"

User-friendly message

"We couldn't connect to the server. Please check your connection and try again."

Error message formula

What happened? Explain
+
Why? When useful
+
What next? Recovery

A useful error message should help the user understand the problem and, when possible, recover from it.

12. Environment Variables

Production applications often need different configuration values for development, testing and production.

.env 
VITE_API_URL=http://localhost:5000/api
React 
const API_URL =
    import.meta.env.VITE_API_URL;

Important security distinction

Configuration

A frontend API base URL may be exposed because the browser needs it.

Secrets

Database passwords, private API keys and server credentials should remain on the server.

13. Security Practices

Production development requires security to be considered throughout the application rather than added at the end.

1
Never expose server secrets

Do not place private credentials inside frontend source code.

2
Validate input

Validate important data on the server even when frontend validation exists.

3
Use HTTPS in production

Production applications should protect network communication with TLS.

4
Do not trust client-side authorization

The backend should enforce authorization rules.

5
Protect authentication credentials

Use an appropriate authentication architecture and avoid unnecessarily exposing sensitive credentials to JavaScript.

6
Do not expose internal errors

Users generally do not need database stack traces or internal server details.

16. Common Production Mistakes

01 — Showing raw technical errors

Avoid exposing stack traces and internal implementation details to normal users.

02 — Handling only successful responses

Real applications must account for failures, empty results and network problems.

03 — No loading state

A blank interface can make users think the application is frozen.

04 — Treating every error as retryable

Some failures require user correction rather than another identical request.

05 — Exposing secrets in frontend code

Browser code is not a secure location for server-only credentials.

06 — Depending only on frontend validation

Important validation and authorization must also be enforced on the backend.

07 — One giant component

Separating UI, API logic and reusable behavior makes applications easier to maintain.

17. Quick Quiz

1. What is the primary purpose of a React Error Boundary?
A. Store data in a database
B. Catch rendering errors in a child component tree and show fallback UI
C. Replace all API authentication
D. Automatically retry every network request
Answer: B — Error Boundaries provide fallback UI for certain rendering errors in their child component tree.
2. What should normally be displayed when an API request is still running?
A. Loading state
B. Empty state only
C. Database credentials
D. Stack trace
Answer: A — A loading state communicates that the asynchronous operation is still in progress.
3. Which HTTP status commonly represents a resource that could not be found?
A. 200
B. 201
C. 404
D. 500
Answer: C — HTTP 404 indicates that the requested resource could not be found.
4. Where should a private database password normally be stored?
A. React JSX
B. Browser source code
C. Server-side configuration
D. Public GitHub README
Answer: C — Private database credentials should remain on the server side.
5. Why are empty states important?
A. They indicate that a successful operation returned no data
B. They replace authentication
C. They automatically fix server errors
D. They store API keys
Answer: A — An empty state gives users useful feedback when there is no content to display.

Production Principle

A professional application is not one where errors never happen. It is one where failures are anticipated, contained, communicated clearly and recovered from whenever possible.


React UI → State → API → Backend → Failure Handling → User Feedback
