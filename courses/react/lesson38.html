1. Why Testing?

Testing means verifying that software behaves as expected under different conditions.

A test is not simply checking whether the code runs. A good test verifies observable behavior and protects important functionality from future changes.
01

Catch Bugs

Tests can detect incorrect behavior before users discover it.

02

Prevent Regression

Existing functionality can be protected when new features are added.

03

Refactor Safely

Tests provide confidence when internal implementation changes.

The Testing Mindset

Write Expected behavior
Run Execute test
Observe Actual result
Compare Expected vs actual
Protect Prevent regression
Professional idea: Tests should give you confidence that important user-visible behavior continues to work after code changes.

2. Unit Testing

A unit test focuses on a small, isolated piece of logic.

Example: Pure Function

math.js 
export function add(a, b) {
    return a + b;
}

A test can verify that the function returns the expected result.

math.test.js 
import { add } from "./math";

test("adds two numbers", () => {
    expect(add(2, 3)).toBe(5);
});

3. Component Testing

Component testing verifies how a React component behaves when rendered and interacted with.

What can be tested?

  • Rendered text
  • Buttons
  • Inputs
  • Conditional UI
  • User interactions
  • Accessible roles

What should matter?

  • User-visible behavior
  • Accessible interactions
  • Important state changes
  • Error states
  • Loading states
  • Success states

Example Component

Counter.jsx 
import { useState } from "react";

export default function Counter() {
    const [count, setCount] = useState(0);

    return (
        <div>
            <p>Count: {count}</p>

            <button onClick={() => setCount(count + 1)}>
                Increment
            </button>
        </div>
    );
}

The test should verify what the user can observe rather than depending on the internal implementation of the component.

5. React Testing Library

React Testing Library is designed around testing React components from the perspective of how users interact with the application.

Core principle: The more your tests resemble the way your software is used, the more confidence they can provide about user-facing behavior.

Important Tools

render()

Renders a React component into the test environment.

screen

Provides queries for finding rendered elements.

userEvent

Simulates realistic user interactions.

Basic Example

Counter.test.jsx 
import { render, screen } from "@testing-library/react";
import Counter from "./Counter";

test("renders counter", () => {
    render(<Counter />);

    expect(
        screen.getByText(/count: 0/i)
    ).toBeInTheDocument();
});

6. Test Structure

A readable test usually follows the Arrange → Act → Assert pattern.

Arrange Prepare the test
Act Perform action
Assert Check result
Cleanup Reset environment
Repeat Independent test

Arrange → Act → Assert

example.test.jsx 
test("increments the counter", async () => {

    // Arrange
    render(<Counter />);

    // Act
    await user.click(
        screen.getByRole("button", {
            name: /increment/i
        })
    );

    // Assert
    expect(
        screen.getByText(/count: 1/i)
    ).toBeInTheDocument();
});
A test should ideally explain the behavior clearly enough that another developer can understand what the application promises.

7. Rendering Components

The render() function mounts a component inside the testing environment.

rendering.test.jsx 
import { render } from "@testing-library/react";
import Welcome from "./Welcome";

test("renders Welcome", () => {
    render(
        <Welcome name="Pradeep" />
    );
});

Testing Props

8. Finding Elements

Testing Library provides different queries for finding elements. Choosing the appropriate query is an important testing skill.

Query Typical Use
getByRole Preferred for accessible interactive/UI elements
getByLabelText Form controls associated with labels
getByText Visible text
getByPlaceholderText Placeholder-based lookup when appropriate
getByTestId Fallback when suitable semantic queries are unavailable
findBy... Elements that appear asynchronously

Prefer Accessible Queries

query.test.jsx 
const button = screen.getByRole(
    "button",
    { name: /submit/i }
);

const emailInput = screen.getByLabelText(
    /email/i
);
Avoid reaching immediately for getByTestId. If the element has a meaningful accessible role or label, testing that user-facing relationship is usually more useful.

9. User Interactions

Modern component tests should model meaningful user interactions.

Using userEvent

interaction.test.jsx 
import userEvent from "@testing-library/user-event";

test("user can increment counter", async () => {

    const user = userEvent.setup();

    render(<Counter />);

    const button = screen.getByRole(
        "button",
        { name: /increment/i }
    );

    await user.click(button);

    expect(
        screen.getByText(/count: 1/i)
    ).toBeInTheDocument();
});

Common Interactions

click()

Buttons, links and interactive controls.

type()

Typing into form controls.

clear()

Removing existing input.

selectOptions()

Changing select controls.

tab()

Keyboard focus movement.

keyboard()

Keyboard interaction scenarios.

When an interaction is asynchronous, await the interaction and use appropriate async assertions when necessary.

10. Testing Forms

Forms are ideal candidates for component testing because they combine input, validation, state and submission behavior.

Example Form

LoginForm.jsx 
function LoginForm() {
    return (
        <form>

            <label htmlFor="email">
                Email
            </label>

            <input
                id="email"
                type="email"
            />

            <button type="submit">
                Login
            </button>

        </form>
    );
}

Testing the Input

LoginForm.test.jsx 
const user = userEvent.setup();

render(<LoginForm />);

const email = screen.getByLabelText(
    /email/i
);

await user.type(
    email,
    "student@example.com"
);

expect(email).toHaveValue(
    "student@example.com"
);

Testing Validation

validation.test.jsx 
await user.click(
    screen.getByRole("button", {
        name: /login/i
    })
);

expect(
    screen.getByText(/email is required/i)
).toBeInTheDocument();
Good form tests verify what the user sees: labels, validation messages, disabled states, submission feedback and successful outcomes.

12. Mocking

Mocking replaces a real dependency with controlled test behavior.

Real Application

React Component

↓

Real API

↓

Real Database

Test Environment

React Component

↓

Mocked API

↓

Controlled Response

Why Mock?

  • Avoid depending on external services.
  • Make tests deterministic.
  • Simulate success responses.
  • Simulate server errors.
  • Test unusual conditions.
  • Keep tests independent from production infrastructure.

Simple Mock Function

mock.test.js 
const getUser = jest.fn();

getUser.mockResolvedValue({
    id: 1,
    name: "Alice"
});

const user = await getUser();

expect(user.name).toBe("Alice");
A mock should represent the dependency behavior required by the test. Over-mocking implementation details can make tests fragile.

13. Async Testing

React applications frequently perform asynchronous work: API calls, delayed UI updates, validation and data loading.

findBy Queries

async.test.jsx 
render(<UserProfile />);

const profile = await screen.findByRole(
    "heading",
    { name: /alice/i }
);

expect(profile).toBeInTheDocument();

waitFor

When an assertion needs to wait for an asynchronous condition, waitFor() can be useful.

wait.test.jsx 
await waitFor(() => {
    expect(
        screen.getByText(/success/i)
    ).toBeInTheDocument();
});
Use async utilities based on the behavior you are testing. Do not add arbitrary delays such as setTimeout() simply to make tests pass.

Async Testing Flow

Render Component
Trigger User action
Wait Async update
Observe New UI
Assert Expected result

14. Test Coverage

Test coverage measures which parts of the codebase are exercised by tests.

92%
85%
74%
68%

Example visualization — statements, branches, functions and lines

Common Coverage Metrics

Metric Meaning
Statements How many executable statements were exercised.
Branches How many conditional paths were exercised.
Functions How many functions were invoked by tests.
Lines How many executable source lines were exercised.
High coverage does not automatically mean high-quality tests. A test suite can execute many lines while failing to verify important behavior.

Better Goal

Aim for meaningful coverage of important behavior and edge cases, not merely a high percentage.

15. Common Mistakes

1. Testing Implementation Details

Tests that depend heavily on internal implementation can break during safe refactoring.

2. Using Test IDs Everywhere

Prefer semantic queries when they represent how users access the UI.

3. Testing Only Success

Loading, empty and error states are important parts of application behavior.

4. Ignoring Accessibility

Accessible labels and roles often make both applications and tests better.

5. Arbitrary Delays

Avoid sleeping for a fixed amount of time when a proper async query can wait.

6. Chasing Coverage

Coverage percentage alone does not prove that behavior is tested correctly.

7. Over-Mocking

Too many mocks can make tests disconnected from real application behavior.

8. One Giant Test

Prefer focused tests that describe individual behaviors clearly.

Professional Testing Checklist

✓ Test important user behavior
✓ Prefer accessible queries
✓ Test success and failure
✓ Handle async behavior correctly
✓ Keep tests independent
✓ Mock external dependencies carefully
✓ Avoid implementation-detail assertions
✓ Use coverage as a signal, not a goal

16. Quick Quiz

Test your understanding before moving to the next React lesson.

Q1. What is the main purpose of a unit test?

To verify a small, isolated piece of logic behaves as expected.

Q2. Which React Testing Library utility renders a component?

The render() function.

Q3. Which query is generally preferred when locating an accessible button?

getByRole() with the appropriate button role and accessible name.

Q4. What does mocking allow you to do?

Replace a real dependency with controlled behavior during a test.

Q5. What should you test for an API-driven component?

Important states such as loading, success, empty results and errors.

Q6. What does test coverage measure?

Which parts of the code are exercised by the test suite, such as statements, branches, functions and lines.

Q7. Why should arbitrary setTimeout() delays usually be avoided?

They make tests slower and less deterministic when proper async testing utilities can wait for the actual UI condition.

Testing is not about proving that every line of code can execute. It is about creating confidence in important application behavior.
