Error Boundaries

Learn how React applications detect rendering failures, isolate broken UI, display fallback interfaces, recover from errors and report failures in production.

Error Boundaries Runtime Errors Fallback UI Recovery Isolation Production Logging
01 • FOUNDATION

What are Error Boundaries?

An Error Boundary is a React component that catches errors thrown during rendering and lifecycle-related work in its descendant tree and replaces the failed portion of the interface with fallback UI.

Without an Error Boundary
React App Application
→
Dashboard Parent
→
Broken Component Throws error
→
Rendering Fails Uncaught boundary

With an Error Boundary
Error Boundary Protects subtree
→
Dashboard Child tree
→
Broken Component Throws error
→
Fallback UI Protected recovery
Think of an Error Boundary as a safety boundary around part of your React UI. If a supported rendering error occurs inside the boundary, React can switch that subtree to fallback content instead of leaving the application without a controlled recovery interface.
02 • RUNTIME RENDERING ERRORS

Runtime Rendering Errors

A runtime error can happen after the application has already loaded. For example, a component might attempt to access something that does not exist while React is rendering.

Problematic Component 
function Profile({ user }) {

    return (
        <div>
            <h2>{user.profile.name}</h2>
        </div>
    );
}

If the expected object structure is missing, rendering can throw an exception.

!

Something went wrong

The component could not render successfully.

Typical Sources

Unexpected Data

A component assumes an object or property exists when the actual data does not contain it.

Component Bugs

A rendering calculation or component operation throws an exception.

Third-Party Components

A library component used by your application can fail while rendering.

Unexpected Application State

A UI path that was rarely used may expose a rendering bug.

03 • FALLBACK UI

Fallback UI

A fallback UI is the interface shown when the protected component tree cannot render normally.

Basic Error Boundary 
import React from "react";

class ErrorBoundary extends React.Component {

    constructor(props) {

        super(props);

        this.state = {
            hasError: false
        };

    }

    static getDerivedStateFromError(error) {

        return {
            hasError: true
        };

    }

    render() {

        if (this.state.hasError) {

            return (
                <div>
                    <h2>
                        Something went wrong.
                    </h2>
                </div>
            );

        }

        return this.props.children;
    }
}
The static getDerivedStateFromError method allows the boundary to update its state so that the next render can display fallback UI.

Good Fallback UI

Clear

Tell the user that this section could not be displayed.

Useful

Provide an appropriate recovery action when one is available.

Localized

When possible, replace only the failed region rather than destroying the entire application's interface.

Accessible

Make the message and recovery controls understandable using normal semantic HTML and accessible labels.

04 • ERROR RECOVERY

Error Recovery

Showing an error message is only part of the recovery strategy. A production interface should consider what the user can do next.

Dashboard unavailable

This section could not be displayed.

Recovery Pattern 
class ErrorBoundary extends React.Component {

    state = {
        hasError: false
    };

    resetError = () => {

        this.setState({
            hasError: false
        });

    };

    render() {

        if (this.state.hasError) {

            return (
                <button
                    onClick={this.resetError}
                >
                    Try Again
                </button>
            );

        }

        return this.props.children;
    }
}
Resetting the boundary state is only a recovery mechanism for the UI. It does not automatically fix the underlying bug. If the same child throws again, the fallback may appear again.

Recovery Strategies

Retry

Allow the user to attempt the operation again when retrying makes sense.

Navigate Away

Move the user to a stable part of the application when the current feature cannot recover.

Reload

For certain deployment or stale-client situations, a full reload can be an appropriate recovery option.

Continue Elsewhere

Keep unaffected application features usable whenever possible.

4. Fallback Alternative UI
5. Report Log the failure

The outer boundary can protect a larger section while nested boundaries can provide more precise isolation for important features.

A good boundary architecture answers one question: “If this feature fails, what other parts of the interface should remain usable?”
07 • ERROR LOGGING

Logging Errors

A fallback tells the user that something went wrong. Logging helps the development team understand what actually failed.

componentDidCatch() 
componentDidCatch(error, errorInfo) {

    console.error(
        "React Error:",
        error
    );

    console.error(
        "Component Stack:",
        errorInfo.componentStack
    );
}

What can be useful to record?

Error Message

The exception's message can help identify the failure.

Stack Information

The stack can provide debugging information about where the error originated.

Component Stack

React can provide component-stack information through the error boundary callback.

Application Context

Useful non-sensitive context can help reproduce and investigate failures.

Production Logging Flow

ERROR: Dashboard rendering failed
Component: AnalyticsPanel
Route: /dashboard
Environment: production
Report queued
Do not blindly send sensitive user information, authentication secrets, tokens or private application data to an external logging service. Logging should follow the application's privacy and security requirements.
08 • PRODUCTION

Production Error Handling

Development error messages are useful for developers, but production users should receive understandable and safe feedback rather than internal implementation details.

Development

  • Detailed stack information
  • Component debugging
  • Console diagnostics
  • Developer-oriented messages
  • Local reproduction

Production

  • User-friendly fallback
  • Error reporting
  • Safe messaging
  • Recovery action
  • Monitoring and investigation

Production Flow

User Uses application
→
Component Error Rendering fails
→
Boundary Catches failure
→
Fallback User sees recovery UI
→
Monitoring Team investigates
Error Boundaries are one layer of production resilience. They should work alongside input validation, API error handling, network handling, loading states, authentication handling and server-side monitoring.
09 • LIMITATIONS

What Error Boundaries Do NOT Catch

Error Boundaries are powerful, but they are not a universal JavaScript error handler.

❌ Event Handlers

Errors thrown directly inside event handlers are not automatically caught by an Error Boundary.

❌ Asynchronous Callbacks

Errors occurring later inside asynchronous callbacks are not generally caught simply because the callback is rendered inside a boundary.

❌ Server-Side Rendering

Client-side Error Boundaries do not replace server-side error handling for server rendering failures.

❌ Boundary Itself

An Error Boundary cannot reliably protect itself from errors in its own implementation.

Event Handler Errors Need Their Own Handling 
function Button() {

    function handleClick() {

        try {

            riskyOperation();

        } catch (error) {

            console.error(error);

            // Handle the event error here
        }
    }

    return (
        <button onClick={handleClick}>
            Save
        </button>
    );
}
Do not think of an Error Boundary as equivalent to a global window.onerror or try/catch around your entire application. It is a React-specific mechanism for isolating supported descendant rendering errors.
10 • PRACTICAL EXAMPLE

Complete Production-Style Error Boundary

Here is a reusable class-based Error Boundary suitable for learning the core architecture.

ErrorBoundary.jsx 
import React from "react";

class ErrorBoundary extends React.Component {

    constructor(props) {

        super(props);

        this.state = {
            hasError: false,
            error: null
        };

    }


    static getDerivedStateFromError(error) {

        return {
            hasError: true,
            error: error
        };

    }


    componentDidCatch(error, errorInfo) {

        console.error(
            "Error Boundary:",
            error
        );

        console.error(
            "Component Stack:",
            errorInfo.componentStack
        );

        // Production:
        // send sanitized information
        // to your monitoring system
    }


    handleRetry = () => {

        this.setState({
            hasError: false,
            error: null
        });

    };


    render() {

        if (this.state.hasError) {

            return (
                <div className="error-fallback">

                    <h2>
                        Something went wrong.
                    </h2>

                    <p>
                        This section could not be displayed.
                    </p>

                    <button
                        onClick={this.handleRetry}
                    >
                        Try Again
                    </button>

                </div>
            );

        }


        return this.props.children;
    }

}


export default ErrorBoundary;

11 • COMMON MISTAKES

Common Error Boundary Mistakes

❌ One Boundary for Everything

A single boundary around the entire application can make recovery less granular.

❌ No Fallback

Catching an error without giving the user useful feedback does not create a good recovery experience.

❌ Hiding Every Error

A fallback should not silently hide failures from the development and monitoring process.

❌ Exposing Stack Traces

Internal debugging details should not be presented directly to ordinary production users.

❌ Assuming Try Again Fixes Bugs

Retrying can reset UI state, but it does not repair a deterministic programming error.

❌ Treating It as Global Error Handling

Event handlers, asynchronous callbacks and other failure sources need their own handling strategies.

12 • CHEAT SHEET

Error Boundary Quick Reference

  • Error Boundary: Protects a descendant React tree from supported rendering errors.
  • getDerivedStateFromError(): Used to update state so the next render can show fallback UI.
  • componentDidCatch(): Useful for side effects such as logging error information.
  • Fallback UI: The safe interface displayed after a supported error.
  • Isolation: Protect meaningful application regions independently.
  • Recovery: Retry, navigate, reload or continue using unaffected features when appropriate.
  • Logging: Record useful diagnostic information while protecting sensitive data.
  • Production: Show safe user-facing messages and send appropriate diagnostic information to monitoring systems.
  • Limitation: Error Boundaries are not universal JavaScript error handlers.
