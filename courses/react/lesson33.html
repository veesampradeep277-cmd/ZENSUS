React Performance Optimization

1. What Causes Re-renders?

A React component can render again when its state changes, when its parent renders, or when the context it consumes changes. A new render does not automatically mean the browser performs a costly DOM update.

State Update

Calling a state setter can schedule another render for the component.

Parent Render

When a parent renders, its child components may render as part of the new tree calculation.

Context Update

Consumers of a changed context value can render again.

Important:

"Re-render" means React runs component rendering logic again. It does not mean React blindly rebuilds the entire browser DOM. React compares the new result with the previous result and commits the necessary changes.

2. The React Render Cycle

Understanding the render pipeline is more important than memorizing optimization APIs.

State / Props Update happens
→
Render Components execute
→
Reconciliation React compares
→
Commit DOM changes
→
Browser Paints UI

Render vs Commit

Render Phase

React calculates what the UI should look like based on the current props, state and context.

Commit Phase

React applies the required changes to the host environment, such as the browser DOM.

Performance insight:

A component rendering again is not necessarily a problem. Optimization should focus on expensive or unnecessary work that actually affects user experience.

3. Component Re-rendering

Consider a parent component containing a counter and a child component. Updating the parent's state can cause the parent to render again and the child to participate in the new render unless React can skip that work.

React example 
function Parent(){

    const [count, setCount] =
        useState(0);

    return (
        <>

                onClick={() =>

The child does not need to receive the parent's changing state to participate in the parent's render tree.

4. React.memo

React.memo can allow a function component to skip a re-render when its props are unchanged according to React's memoization comparison.

Without memo

function UserCard({ user }){

    return (
        <div>
            {user.name}
        </div>
    );
}

With memo

const UserCard =
    React.memo(function UserCard({
        user
    }){

        return (
            <div>
                {user.name}
            </div>
        );

    });

Without Memo

A parent render can cause the child to render again even if the child receives the same logical props.

With Memo

React can skip the child render when the relevant props compare equal.

Important limitation

If you create a new object or function on every parent render and pass it as a prop, the prop reference can change even when its contents look the same. 

const user = {
    name: "Pradeep"
};

<UserCard user={user} />

If that object is recreated during every parent render, memoization may not provide the expected benefit.

5. useMemo

useMemo can cache the result of a calculation between renders until its dependencies change.

Expensive calculation example

const filteredProducts =
    useMemo(() => {

        return products.filter(
            product =>
                product.price > 1000
        );

    }, [products]);

Conceptual flow

Products Input
→
Calculation Potentially expensive
→
Memoized Result Cached value
Do not use useMemo everywhere.

Memoization itself has a cost. It is most useful when a calculation is meaningfully expensive or when stable derived values are important for another optimization.

6. useCallback

useCallback can preserve the same function reference between renders until its dependencies change. 

const handleDelete =
    useCallback((id) => {

        deleteProduct(id);

    }, [deleteProduct]);

Why function identity matters

Parent Render Runs again
→
Function Creation New reference
→
Memoized Child Prop changed

If a callback is passed to a memoized child, useCallback can sometimes help keep the callback reference stable.

useMemo vs useCallback

Hook Memoizes Typical Purpose
useMemo A calculated value Avoid repeating expensive calculations.
useCallback A function reference Keep callbacks stable when reference identity matters.
Key idea:

useCallback does not automatically make the callback itself execute faster. It mainly preserves function identity.

7. Code Splitting

Code splitting divides JavaScript into smaller chunks so that the browser does not necessarily have to download the entire application before displaying the initial UI.

Large App All code
→
Build Tool Splits modules
→
Chunk A Home
Chunk B Dashboard
Chunk C Admin

Why code splitting matters

Smaller Initial Download

The browser can avoid downloading unrelated application code immediately.

Faster Startup

Less JavaScript may need to be downloaded and processed initially.

Route-Based Loading

Large application areas can be loaded when users navigate to them.

8. Lazy Loading

React.lazy allows a component to be loaded dynamically. Suspense provides a fallback while that lazy component is being loaded. 

import {
    lazy,
    Suspense
} from "react";

const Dashboard =
    lazy(() =>
        import("./Dashboard")
    );

function App(){

    return (
        <Suspense
            fallback={
                <p>
                    Loading dashboard...
                </p>
            }
        >

            <Dashboard />

        </Suspense>
    );
}

Typical use cases

Dashboard

Load complex dashboard code when the user opens it.

Admin Panel

Administrative features may not be needed by normal users.

Large Editor

Load a heavy editor only when required.

Lazy loading is a delivery optimization.

It does not make the component's JavaScript intrinsically faster. It changes when that code is downloaded and evaluated.

9. Bundle Size

The JavaScript bundle contains application code and dependencies that must be delivered to the browser. Large bundles can increase download, parse and evaluation work.

Dependencies

Review whether every package is actually necessary.

Tree Shaking

Modern build systems can remove unused statically analyzable code.

Dynamic Imports

Split features that do not need to be loaded immediately.

Bundle optimization questions

• Do we need this dependency?

• Is the entire library being imported?

• Can this feature be lazy loaded?

• Are large assets being downloaded unnecessarily?

• Can route-level code splitting reduce the initial bundle?

10. Expensive Calculations

Some operations are expensive enough to noticeably affect rendering. Examples include processing thousands of records, complex filtering, sorting, parsing or heavy computations.

Bad pattern

function Dashboard({ products }){

    const result =
        veryExpensiveCalculation(products);

    return (
        <Result value={result} />
    );
}

If the calculation runs during every render, unrelated state updates can cause the calculation to run again.

Possible optimization

const result = useMemo(() => {

    return veryExpensiveCalculation(
        products
    );

}, [products]);
Optimization principle:

First determine whether the calculation is actually expensive. Do not assume that every calculation requires memoization.

11. List Optimization

Large lists can become expensive because many elements may need to be rendered, updated and committed.

Always use stable keys

products.map(product => (

    <ProductCard
        key={product.id}
        product={product}
    />

));

Good Key

key={product.id}

A stable identity from the data.

Potentially Problematic

key={index}

Using array indexes can cause identity problems when items are inserted, removed or reordered.

Large list strategies

Pagination

Show a manageable portion of the data at a time.

Virtualization

Render only the rows that are currently needed for the visible area.

Memoized Items

Prevent unchanged list items from doing unnecessary render work when appropriate.

12. React DevTools Profiler

The React DevTools Profiler helps developers investigate rendering behavior and identify components that are consuming significant render time.

Illustrative Profiler Timeline

What to investigate

Frequent Renders

Does a component render much more often than necessary?

Expensive Components

Does one component consume significant rendering time?

Interaction Lag

Does a user interaction produce noticeable delay?

Profiler mindset:

Do not optimize a component simply because it appears in the profiler. Look for meaningful performance problems and then test whether the optimization actually improves them.

14. Common Optimization Mistakes

!
Using useMemo everywhere

Memoization has overhead. Use it when there is a meaningful reason.

!
Using useCallback everywhere

A stable callback is not automatically a performance improvement.

!
Thinking every re-render is bad

Rendering is a normal part of React. Optimize actual bottlenecks.

!
Optimizing before measuring

Without a baseline, you may optimize the wrong part of the application.

!
Using array indexes as keys everywhere

Keys should represent stable item identity whenever possible.

!
Lazy loading everything

Too many small chunks can also create additional loading complexity. Split meaningful boundaries rather than blindly splitting every component.

!
Assuming memoization fixes slow code

If the real bottleneck is network latency, heavy computation or a huge bundle, React.memo alone will not solve it.

16. Quick Quiz

1. Which of the following can cause a React component to render again?
A. A state update
B. A parent render
C. A consumed context value changing
D. All of the above
Answer: D — state updates, parent rendering, and relevant context changes can all cause rendering work.
2. What does React.memo primarily optimize?
A. Database queries
B. Component rendering when props have not meaningfully changed
C. Network speed
D. CSS compilation
Answer: B — React.memo can allow a component to skip rendering when its props compare equal.
3. What does useMemo cache?
A. A calculated value
B. A database
C. A CSS stylesheet
D. An HTTP server
Answer: A — useMemo caches the result of a calculation until its dependencies change.
4. What does useCallback primarily preserve?
A. A function reference
B. A database connection
C. An HTML element
D. An image file
Answer: A — useCallback can preserve a function reference between renders until its dependencies change.
5. What is a major purpose of code splitting?
A. Increase the initial JavaScript download
B. Divide application code into separately loaded chunks
C. Remove React from the project
D. Replace CSS with JavaScript
Answer: B — code splitting allows application code to be divided into chunks that can be loaded separately.
6. Which tool is specifically useful for investigating React component rendering performance?
A. React DevTools Profiler
B. package.json
C. HTML validator
D. CSS reset
Answer: A — the React DevTools Profiler helps investigate React rendering behavior and timing.
7. What is the recommended general order for performance optimization?
A. Optimize everything immediately
B. Measure → identify bottleneck → optimize → measure again
C. Add useMemo to every component
D. Replace all state with Redux
Answer: B — performance work should be measurement-driven and verified after optimization.

The ZENSUS Performance Mindset

Do not optimize React because you can. Optimize because you measured a real problem.
