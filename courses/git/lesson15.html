1. The Complete Project Scenario

Imagine you are building a small web application called StudentHub.

The application allows students to register, log in, view their profile, and manage their courses.

Frontend

Login page, dashboard, profile and course screens.

Backend

Authentication, student APIs and database logic.

GitHub

Source control, collaboration, pull requests and project history.

2. Create the Local Project

Start by creating the project directory on your computer. 

mkdir studenthub
cd studenthub

git init

git status
Result: The folder is now a Git repository and Git can track changes inside it.

3. Build the Initial Project

Add your project files. 

studenthub/
│
├── frontend/
│   ├── index.html
│   ├── styles.css
│   └── app.js
│
├── backend/
│   ├── app.py
│   └── requirements.txt
│
├── README.md
└── .gitignore

Before the first commit, check what Git sees. 

git status

4. Stage and Create the First Commit

Review the files, stage the intended changes, and create the first snapshot. 

git add .

git diff --staged

git commit -m "Initialize StudentHub project"
Remember: git add selects changes for the next commit. git commit creates the snapshot in local Git history.

5. Connect the Local Repository to GitHub

Create an empty repository on GitHub and connect it as the remote named origin. 

git remote add origin <your-repository-url>

git remote -v

git branch -M main

git push -u origin main
Now: Your local project history has been pushed to the GitHub repository.

6. Create a Feature Branch

Do not make every change directly on the main branch in a collaborative workflow. 

git switch main

git pull

git switch -c feature/student-login

main

Stable project branch.

feature/student-login

Isolated development branch.

Pull Request

Used later to propose the change for review.

8. Review, Commit and Push 

git status

git diff

git add .

git diff --staged

git commit -m "Add student login feature"

git push -u origin feature/student-login

The feature branch is now available on GitHub.

9. Open a Pull Request

A Pull Request asks the team to review the changes before they are integrated into the main branch.

feature/student-login Your changes
→
Pull Request Review request
→
main Target branch

A Good Pull Request Contains

  • Clear title.
  • Explanation of the change.
  • Testing information.
  • Screenshots when useful.
  • Related issue reference.

10. Code Review

Another developer reviews the Pull Request.

🔍 Correctness

Does the feature behave correctly?

🧹 Code Quality

Is the implementation readable and maintainable?

🛡️ Security

Are sensitive values and authentication handled safely?

Review cycle: Comment → Developer updates code → Commit → Push → Pull Request updates automatically.

11. Automated CI Checks

GitHub Actions can automatically run checks when code is pushed or when a Pull Request is created. 

name: StudentHub CI

on:
  push:
    branches: [main]

  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Run tests
        run: |
          echo "Running project tests"
          echo "Tests completed"

The workflow can report whether automated checks passed or failed.

CI idea: Every important change should be checked automatically before it becomes part of the stable branch.

14. Tag a Release

Tags can identify important versions of a project. 

git tag v1.0.0

git push origin v1.0.0

A release can represent a stable milestone such as v1.0.0.

Semantic versioning example:

MAJOR.MINOR.PATCH

Example: 2.4.1

18. Complete Command Flow

A simplified project workflow can look like this: 

# Start
git init

# Check
git status

# Create branch
git switch -c feature/my-feature

# Work on files

# Review
git status
git diff

# Stage
git add .

# Review staged changes
git diff --staged

# Commit
git commit -m "Add my feature"

# Push
git push -u origin feature/my-feature

# After review and merge
git switch main
git pull

# Release
git tag v1.0.0
git push origin v1.0.0

20. Final Git Best Practices

Practice Why It Matters
Check git status Know what branch and changes you are working with.
Use feature branches Keep work isolated from stable code.
Write clear commits Make project history understandable.
Review before commit Avoid accidentally committing unwanted files.
Protect secrets Reduce credential exposure.
Use Pull Requests Enable review and controlled integration.
Automate tests Catch problems consistently.
Keep main stable Maintain a reliable shared branch.
Tag releases Identify important project versions.
