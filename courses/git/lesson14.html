GIT & GITHUB • LESSON 14

Git Best Practices & Common Git Mistakes

Learn how to use Git professionally, write useful commits, manage branches safely, protect sensitive files, avoid common mistakes, and recover when something goes wrong.

1. Why Git Best Practices Matter

Git becomes much more useful when a project follows a consistent workflow.

Good Git practices help teams:

🧭 Understand History

Clear commits make it easier to understand why a change was made.

🤝 Collaborate

Consistent branches and commits make teamwork easier.

🛡️ Reduce Risk

Safe workflows reduce accidental data loss.

🔍 Review Code

Small focused commits are easier to inspect.

🚀 Automate

Clean repositories work better with CI/CD pipelines.

📚 Maintain Projects

Future developers can understand the repository faster.

2. Write Good Commit Messages

A commit message should describe what changed.

✓ Good 

git commit -m "Add student registration form"

git commit -m "Fix login validation error"

git commit -m "Update dashboard layout"

✕ Weak 

git commit -m "update"

git commit -m "changes"

git commit -m "stuff"

git commit -m "final"

What Makes a Good Commit?

  • Describe the main change.
  • Keep the message concise.
  • Use meaningful language.
  • Avoid vague messages.
  • Prefer focused commits over unrelated collections of changes.
Example:

Instead of: git commit -m "fix"
Prefer: git commit -m "Fix invalid email validation"

3. Keep Commits Focused

A focused commit contains one logical change.

Change Fix login bug
→
Stage Related files
→
Commit Clear message
→
Review Easy to understand

✓ Focused

Fix login validation

Only the files related to the login validation change are included.

✕ Unfocused

Update everything

Login, dashboard, database, documentation, and unrelated formatting are all committed together.

4. Branch Management Best Practices

Branches allow developers to work on changes independently. Good branch habits make collaboration safer.

Use descriptive names 

feature/login-page
feature/payment-api
bugfix/navbar-error
docs/setup-guide

Avoid vague names 

branch1
test
new
mybranch
changes

Useful Branch Commands 

git branch
git switch main
git switch -c feature/login-page
git branch -d feature/login-page
Good habit: Keep the main branch stable and use feature or bug-fix branches for active development when working in a team.

5. Keep Your Local Repository in Sync

Before starting work or pushing changes in a team project, it is important to understand what has changed on the remote.

Inspect First 

git status
git fetch origin
git status

Pull Changes 

git pull
Important: Do not blindly overwrite other people's work. Understand your local changes and remote changes before resolving conflicts.

6. Use .gitignore Correctly

The .gitignore file tells Git which files or directories should not normally be tracked.

Common Things to Ignore

  • dependency folders
  • build output
  • temporary files
  • editor-specific files
  • local environment files
  • operating-system-specific files

Example 

node_modules/
.env
__pycache__/
*.log
dist/
.vscode/
Important: Adding a file to .gitignore does not automatically remove a file that Git is already tracking.

Stop Tracking an Already-Tracked File 

git rm --cached .env
git commit -m "Stop tracking environment file"

7. Never Commit Secrets

One of the most important Git security practices is keeping credentials out of the repository.

API Keys

Keep API credentials outside source control.

Passwords

Never store database or service passwords in code.

Tokens

Protect access tokens and authentication credentials.

Bad Example 

API_KEY = "123456789-secret-key"

Better Approach 

API_KEY = os.getenv("API_KEY")
If a secret is accidentally committed: Removing it from the latest file is not necessarily enough. The secret may still exist in repository history.

Treat an exposed credential as compromised and rotate or revoke it through the relevant service.

8. Be Careful When Rewriting History

Git allows you to modify local history, but some operations can affect shared branches.

Soft Reset 

git reset --soft HEAD~1

Moves the branch pointer back while keeping changes staged.

Mixed Reset 

git reset HEAD~1

Moves the branch pointer back and unstages the changes, while keeping the working files.

Hard Reset 

git reset --hard HEAD~1
Caution: --hard can discard working-tree changes. Do not use it casually when you have work you may need.

Reverting a Shared Commit 

git revert <commit-id>

git revert creates a new commit that reverses the effect of an earlier commit. This is often safer for shared history than rewriting the existing commits.

9. Common Git Mistakes

Mistake What Can Happen Better Practice
Commit directly to the wrong branch Changes may end up in an unintended branch. Check git status and branch name first.
Commit secrets Credentials may be exposed. Use environment variables and secure secret storage.
Huge commits Changes become difficult to review. Make smaller logical commits.
Vague commit messages History becomes difficult to understand. Write descriptive messages.
Ignoring remote changes Pushes may be rejected or conflicts may appear. Fetch/pull and understand remote changes.
Force pushing carelessly Shared branch history can be overwritten. Avoid unnecessary force pushes.
Using git reset --hard blindly Local changes can be discarded. Inspect status and protect important work first.

10. Useful Recovery Commands

Mistakes happen. Git provides several tools that can help you inspect or recover from common situations.

Check Current State 

git status

Shows the current branch and working-tree state.

Inspect Recent History 

git log --oneline -5

Shows recent commits in compact form.

Find Previous HEAD Positions 

git reflog

Shows movements of HEAD and can help locate commits after some local history changes.

Inspect a Commit 

git show <commit-id>

Displays information about a specific commit.

Recovery principle: Before running a destructive command, stop and inspect the repository state. If you are unsure, avoid making additional destructive changes until you understand what happened.

11. Be Careful With Force Push

A force push can replace remote branch history with your local history. 

git push --force

A safer alternative in many situations is: 

git push --force-with-lease
Warning: Force pushing shared branches can overwrite other people's work. Understand the branch policy before using it.

12. Recommended Professional Workflow

A simple team workflow can look like this:

1. Sync Fetch / pull
→
2. Branch Feature branch
→
3. Develop Write code
→
4. Test Verify locally
→
5. Commit Clear message
→
6. Push Remote branch
→
7. Review Pull request
→
8. Merge Integrate

Before You Push 

git status
git diff
git add .
git diff --staged
git commit -m "Describe the change"
git push
Simple rule: Inspect → Change → Test → Stage → Review → Commit → Push.

17. Lesson Takeaway

Professional Git usage is not only about knowing commands. It is also about using those commands safely and consistently.

  • Write clear and meaningful commit messages.
  • Keep commits focused on one logical change.
  • Use descriptive branch names.
  • Check git status before important operations.
  • Review changes with git diff before committing.
  • Use .gitignore for files that should not normally be tracked.
  • Never commit passwords, API keys, or other sensitive credentials.
  • Be careful with git reset --hard.
  • Avoid unnecessary force pushes on shared branches.
  • Use git revert when you need to create a new commit that reverses an earlier shared commit.
  • Use git reflog when investigating local history movements.
