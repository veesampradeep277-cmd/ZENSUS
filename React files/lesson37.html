01 • FOUNDATION

Why TypeScript?

JavaScript is dynamically typed. TypeScript adds static type checking so many incorrect assumptions can be detected during development.

JavaScript vs TypeScript
JavaScript Write code
→
Runtime Problems may appear
VS
TypeScript Typed source
→
Type Checker Finds many mistakes

Early Error Detection

TypeScript can detect many type-related mistakes before the application runs.

Better Autocomplete

Editors can understand the shape of objects and provide stronger autocomplete.

Safer Refactoring

Explicit types make large codebase changes easier to reason about.

Clear Data Contracts

Types document what components, functions and APIs expect.

TypeScript does not automatically validate runtime API data. External data may still require runtime validation.

Props Types

Props are data passed from a parent component to a child component. TypeScript lets us define the expected props.

Button.tsx Typed Props 
type ButtonProps = {
    label: string;
    disabled?: boolean;
    onClick: () => void;
};

function Button({
    label,
    disabled = false,
    onClick
}: ButtonProps) {

    return (
        <button
            disabled={disabled}
            onClick={onClick}
        >
            {label}
        </button>
    );
}

export default Button;

06 • STATE

State Types

React state can be typed explicitly when the state has multiple possible values or when inference is not enough.

Component.tsx Primitive State 
const [count, setCount] =
    useState<number>(0);

const [name, setName] =
    useState<string>("");

const [isOpen, setIsOpen] =
    useState<boolean>(false);
Component.tsx Object State 
interface User {

    name: string;

    email: string;

}

const [user, setUser] =
    useState<User | null>(null);
Component.tsx Array State 
const [users, setUsers] =
    useState<User[]>([]);
Do not manually type every simple value. TypeScript can infer many obvious state types automatically.

React Reducer Types 
type State = {

    count: number;

};

type Action =
    | { type: "increment" }
    | { type: "decrement" };

function reducer(
    state: State,
    action: Action
): State {

    switch(action.type) {

        case "increment":

            return {
                count: state.count + 1
            };

        case "decrement":

            return {
                count: state.count - 1
            };

        default:

            return state;
    }
}

Redux with TypeScript

Redux Toolkit provides a strong foundation for typed global state.

import {
    configureStore
} from "@reduxjs/toolkit";

import counterReducer
    from "./counterSlice";

export const store =
    configureStore({

        reducer: {

            counter:
                counterReducer

export type RootState =
    ReturnType<
        typeof store.getState
    >;

export type AppDispatch =
    typeof store.dispatch;
hooks.ts Typed Redux Hooks 
import {
    useDispatch,
    useSelector
} from "react-redux";

import type {
    RootState,
    AppDispatch
} from "./store";

export const useAppDispatch =
    useDispatch.withTypes<AppDispatch>();

export const useAppSelector =
    useSelector.withTypes<RootState>();

15 • QUALITY

Common Mistakes

❌ Using any Everywhere

Using any removes much of TypeScript's protection.

❌ Overusing Assertions

Assertions tell TypeScript to trust your assumption; they do not validate runtime data.

❌ Trusting API Types Blindly

External JSON can still be malformed even when a TypeScript interface describes the expected structure.

❌ Duplicating Types

Repeated models can drift apart and become difficult to maintain.

❌ Typing Everything Manually

TypeScript inference can handle many obvious cases automatically.

❌ Ignoring Strictness

Weak compiler settings can reduce the protection TypeScript provides.

❌ Confusing Compile-Time and Runtime

TypeScript checks source code but does not automatically validate every runtime value.

❌ Giant Interfaces

Large types can become difficult to understand. Prefer focused models.

17 • KNOWLEDGE CHECK

Quick Quiz

React + TypeScript Mindset

Don't add types just to make TypeScript happy. Design useful data contracts for components, state, APIs and application logic. Let TypeScript catch incorrect assumptions early while remembering that runtime data still needs appropriate validation.
