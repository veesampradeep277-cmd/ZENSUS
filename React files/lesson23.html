REACT STATE ARCHITECTURE

Context + Reducer

Combine Context API with useReducer() to build organized shared-state architecture for React applications.

1. Why Combine Context and Reducer?

In the previous lessons you learned two separate concepts:

Context Makes a value available to components without manually passing it through every intermediate component.
useReducer() Centralizes complex state transition logic using actions and a reducer.

When combined, they solve two different problems:

Reducer
+
Context
=
Shared State Architecture
Core Idea:

Context answers: “Who can access this state?”

Reducer answers: “How can this state change?”

This pattern is useful when many components need to read and/or update the same related state.

2. Global State Architecture

Applications often have state that multiple distant components need.

Examples include:

Authentication Current user and authentication-related UI state.
Shopping Cart Items, quantities and cart operations.
Theme Application-wide appearance preference.
Language Selected application language.
Notifications Shared notification state.
Application Workflow State shared across several related screens.
Important: “Global state” does not mean every piece of state should live at the top of the application. Keep state local when only one component or small subtree needs it.

3. Context Provider

A common architecture is to create a Context and a dedicated Provider component. 

import {
    createContext,
    useContext,
    useReducer
} from "react";

const AppContext = createContext(null);

function AppProvider({ children }) {

    const [state, dispatch] =
        useReducer(reducer, initialState);

    return (
        <AppContext.Provider
            value={{ state, dispatch }}
        >
            {children}
        </AppContext.Provider>
    );
}

Components below the Provider can access the context. 

function Dashboard() {

    const { state, dispatch } =
        useContext(AppContext);

    return (
        <h1>{state.user.name}</h1>
    );
}
Architecture separation:

Provider → owns and distributes state
Reducer → defines state transitions
Components → display state and dispatch actions

4. Reducer Logic

The reducer remains the central place where state transitions are defined. 

const initialState = {
    user: null,
    loading: false,
    error: null
};

function reducer(state, action) {

    switch (action.type) {

        case "LOGIN_START":
            return {
                ...state,
                loading: true,
                error: null
            };

        case "LOGIN_SUCCESS":
            return {
                ...state,
                loading: false,
                user: action.payload
            };

        case "LOGIN_ERROR":
            return {
                ...state,
                loading: false,
                error: action.payload
            };

        case "LOGOUT":
            return {
                ...initialState
            };

        default:
            return state;
    }
}

Notice that the reducer does not know which component dispatched the action.

It only understands:

Current State
+
Action
→
Next State

5. Dispatching Actions

Components don't directly modify reducer state. They dispatch actions. 

dispatch({
    type: "LOGIN_SUCCESS",
    payload: user
});

Component Responsibility

function LoginButton() {

    const { dispatch } =
        useContext(AppContext);

    function handleLogin() {

        dispatch({
            type: "LOGIN_SUCCESS",
            payload: {
                name: "Pradeep"
            }
        });
    }

    return (
        <button onClick={handleLogin}>
            Login
        </button>
    );
}
The component describes the event. The reducer owns the state transition.

7. Authentication Example

Authentication-related UI state is a common example of Context + Reducer architecture.

State

const initialState = {
    user: null,
    status: "loggedOut",
    error: null
};

Reducer

function authReducer(state, action) {

    switch (action.type) {

        case "LOGIN_START":
            return {
                ...state,
                status: "loading",
                error: null
            };

        case "LOGIN_SUCCESS":
            return {
                user: action.payload,
                status: "loggedIn",
                error: null
            };

        case "LOGIN_ERROR":
            return {
                ...state,
                status: "error",
                error: action.payload
            };

        case "LOGOUT":
            return {
                user: null,
                status: "loggedOut",
                error: null
            };

        default:
            return state;
    }
}

Provider

const AuthContext = createContext(null);

function AuthProvider({ children }) {

    const [state, dispatch] =
        useReducer(
            authReducer,
            initialState
        );

    return (
        <AuthContext.Provider
            value={{ state, dispatch }}
        >
            {children}
        </AuthContext.Provider>
    );
}

Consumer

function UserProfile() {

    const { state } =
        useContext(AuthContext);

    if (state.status === "loading") {
        return <p>Logging in...</p>;
    }

    if (state.status === "loggedOut") {
        return <p>Please log in.</p>;
    }

    return (
        <h2>
            Welcome {state.user.name}
        </h2>
    );
}
This architecture manages client-side UI/application state. It does not make authentication secure by itself. Credentials, tokens, authorization and server-side access control must be handled according to the application's security architecture.

8. Shopping Cart Example

A shopping cart demonstrates why Context + Reducer can be useful: multiple components may need access to the same cart.

ProductCard Adds products.
CartIcon Displays item count.
CartPage Displays cart items.
Checkout Reads cart information.

Initial State

const initialState = {
    items: []
};

Reducer

function cartReducer(state, action) {

    switch (action.type) {

        case "ADD_ITEM":

            return {
                ...state,
                items: [
                    ...state.items,
                    action.payload
                ]
            };

        case "REMOVE_ITEM":

            return {
                ...state,
                items: state.items.filter(
                    item =>
                        item.id !== action.payload
                )
            };

        case "CLEAR_CART":

            return {
                ...state,
                items: []
            };

        default:
            return state;
    }
}

Cart Provider

const CartContext = createContext(null);

function CartProvider({ children }) {

    const [state, dispatch] =
        useReducer(
            cartReducer,
            initialState
        );

    return (
        <CartContext.Provider
            value={{ state, dispatch }}
        >
            {children}
        </CartContext.Provider>
    );
}

Product Component

function ProductCard({ product }) {

    const { dispatch } =
        useContext(CartContext);

    return (
        <button
            onClick={() =>
                dispatch({
                    type: "ADD_ITEM",
                    payload: product
                })
            }
        >
            Add to Cart
        </button>
    );
}

9. Custom Hook for Cleaner Context Access

Instead of repeating useContext() everywhere, a dedicated custom Hook can make the architecture easier to use. 

const CartContext = createContext(null);

export function useCart() {

    const context =
        useContext(CartContext);

    if (!context) {
        throw new Error(
            "useCart must be used inside CartProvider"
        );
    }

    return context;
}

Then components can write:

function CartButton() {

    const { dispatch } = useCart();

    return (
        <button
            onClick={() =>
                dispatch({
                    type: "ADD_ITEM",
                    payload: product
                })
            }
        >
            Add to Cart
        </button>
    );
}
This creates a cleaner public API for your feature: components think in terms of useCart(), while the provider and reducer remain implementation details.

11. Scaling the Pattern

Context + Reducer can work well for a feature with shared state, but architecture should evolve with application requirements.

Small Application

Component
→
useState

Medium Shared Feature

Components
→
Context
→
Reducer

Larger Application

Feature Modules
→
State Architecture
→
Server/API

Separate State by Domain

Auth State user, status, errors
Cart State items, quantities
Theme State theme preference
UI State modals, panels, selections
Do not automatically create one enormous Context containing every piece of application state. Different state domains can have different ownership and update requirements.

Context Re-render Consideration

When a Provider's context value changes, consumers that read that context can re-render.

This is one reason to keep contexts focused and to avoid putting unrelated rapidly changing data into a single context.

12. Common Mistakes

❌ Mistake 1 — Treating Context as a Reducer

Context provides values. It does not replace reducer logic. 

Context
    ↓
Provides state + dispatch

Reducer
    ↓
Defines transitions

❌ Mistake 2 — Mutating Reducer State

state.items.push(item);

return state;

Prefer immutable updates:

return {
    ...state,
    items: [
        ...state.items,
        item
    ]
};

❌ Mistake 3 — Putting Side Effects in Reducers

function reducer(state, action) {

    fetch("/api/user"); // ❌

    return state;
}

Reducers should remain pure.

❌ Mistake 4 — One Giant Context

Combining authentication, cart, theme, notifications and every other state domain into one Context can make the architecture harder to reason about.

❌ Mistake 5 — Using Context When Props Are Simpler

For a direct parent-child relationship, ordinary props can be clearer than Context.

❌ Mistake 6 — Assuming Context Makes Data Secure

Context is a React state-sharing mechanism. It is not an authentication or authorization security boundary.

❌ Mistake 7 — Provider Placement Is Wrong

A component can only consume a Context value from a matching Provider above it in the React tree. 

<AuthProvider>

    <Dashboard />

</AuthProvider>

Putting Dashboard outside the Provider means it cannot consume that Provider's value.

13. Context vs Reducer vs Context + Reducer

Pattern Main Responsibility Typical Use
useState Simple state Local component state
useReducer Complex transitions Complex local/feature state
Context Value distribution Shared values across descendants
Context + Reducer Shared complex state Feature-level application state
Remember:

Context ≠ state management rules.
Reducer ≠ state distribution.

Context + Reducer = a useful pattern for distributing and managing shared state.

14. Complete Architecture Example

// CartContext.jsx

import {
    createContext,
    useContext,
    useReducer
} from "react";

const CartContext =
    createContext(null);

const initialState = {
    items: []
};

function cartReducer(state, action) {

    switch (action.type) {

        case "ADD_ITEM":

            return {
                ...state,
                items: [
                    ...state.items,
                    action.payload
                ]
            };

        case "REMOVE_ITEM":

            return {
                ...state,
                items: state.items.filter(
                    item =>
                        item.id !== action.payload
                )
            };

        case "CLEAR_CART":

            return {
                ...state,
                items: []
            };

        default:
            return state;
    }
}

export function CartProvider({ children }) {

    const [state, dispatch] =
        useReducer(
            cartReducer,
            initialState
        );

    return (
        <CartContext.Provider
            value={{ state, dispatch }}
        >
            {children}
        </CartContext.Provider>
    );
}

export function useCart() {

    const context =
        useContext(CartContext);

    if (!context) {
        throw new Error(
            "useCart must be used inside CartProvider"
        );
    }

    return context;
}

App.jsx

import {
    CartProvider
} from "./context/CartContext";

function App() {

    return (
        <CartProvider>

            <Header />

            <ProductList />

            <Cart />

            <Checkout />

        </CartProvider>
    );
}

Any Consumer

function Cart() {

    const {
        state,
        dispatch
    } = useCart();

    return (
        <div>

            <h2>
                Cart: {state.items.length}
            </h2>

            <button
                onClick={() =>
                    dispatch({
                        type: "CLEAR_CART"
                    })
                }
            >
                Clear Cart
            </button>

        </div>
    );
}
This is the complete architecture:

Provider → Context → Consumer → dispatch → Reducer → New State → Consumer
