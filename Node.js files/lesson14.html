02 • API Testing

What Is API Testing?

API testing is the process of sending requests to an API and checking whether the server returns the expected result.

Instead of testing only the user interface, API testing directly tests the backend logic, database operations, authentication, validation, error handling, and response structure.

Simple Definition API testing means: Send a request → Receive a response → Verify the response.
Client Request
→
Express API Process
→
Database Read / Write
→
Response JSON
→
Test Verify

Why Do We Test APIs?

  • To verify that endpoints work correctly.
  • To detect bugs before deployment.
  • To verify HTTP status codes.
  • To check response data.
  • To test invalid input.
  • To verify authentication and authorization.
  • To test database operations.
  • To prevent previously fixed bugs from returning.
03 • Testing Methods

Manual vs Automated API Testing

👨‍💻

Manual Testing

A developer manually sends API requests using tools such as Postman or Thunder Client.

Example

Send: GET /api/users

Then inspect the response manually.

Useful for:
  • Exploration
  • Debugging
  • Quick checks
  • Learning APIs
🤖

Automated Testing

Code automatically sends requests and checks whether the expected results are returned.

Example

The test automatically verifies:

  • Status code = 200
  • Response contains users
  • Response is JSON
  • Required properties exist
Professional Workflow Use manual testing while developing and debugging, then use automated tests to repeatedly verify important functionality.

06 • Postman

Testing APIs with Postman

Postman is one of the most commonly used tools for manually testing APIs. It allows developers to create requests, send them to servers, inspect responses, organize endpoints into collections, and automate tests.

Basic Postman Workflow

Select Method GET / POST
→
Enter URL API endpoint
→
Add Data Body / Headers
→
Send Request
→
Verify Response

Important Postman Features

Collections

Group related API requests together.

Environments

Store variables such as base URLs and tokens.

Variables

Reuse values such as {{baseUrl}}.

Authorization

Send Bearer tokens, API keys, Basic Auth, etc.

Tests

Automatically verify response conditions.

Runner

Execute multiple requests and tests together.

Example Postman Test

Postman Test 
pm.test("Status code is 200", function () {
  pm.response.to.have.status(200);
});

pm.test("Response is JSON", function () {
  pm.response.to.be.json;
});

pm.test("User object exists", function () {
  const data = pm.response.json();

  pm.expect(data).to.have.property("user");
});
07 • Automated Testing

Jest + Supertest

Manual testing is useful, but manually repeating hundreds of requests becomes inefficient. Automated testing solves this problem.

Jest

Jest is a JavaScript testing framework used to create and execute automated tests.

Supertest

Supertest allows us to send HTTP requests directly to an Express application during testing.

Install Testing Packages

Terminal
npm install --save-dev jest supertest

Example Test

user.test.js
const request = require("supertest");
const app = require("../app");

describe("User API", () => {

  test("GET /api/users should return 200", async () => {

    const response = await request(app)
      .get("/api/users");

    expect(response.statusCode).toBe(200);

    expect(response.body)
      .toHaveProperty("users");

  });

});

Run Tests

Terminal
npx jest
PASS tests/user.test.js ✓ GET /api/users should return 200 Test Suites: 1 passed Tests: 1 passed

Positive and Negative Tests

Positive Test

Verify that valid input produces the expected successful result.

Example: valid login → 200 OK

Negative Test

Verify that invalid input is rejected correctly.

Example: invalid login → 401 Unauthorized

09 • Production Preparation

Preparing an API for Production

Development environments are designed for fast development. Production environments require additional reliability, security, monitoring, and performance considerations.

Development

Debugging enabled, local database, frequent code changes.

Testing

Automated tests, controlled test database, repeatable test scenarios.

Production

HTTPS, monitoring, secure secrets, reliable database, optimized configuration.

NODE_ENV

Environment Check
if (process.env.NODE_ENV === "production") {
  console.log("Production mode enabled");
}

Production Error Handling

Detailed internal errors should not be exposed to users. A production API should log the real error internally and return a safe message to the client.

errorHandler.js
function errorHandler(err, req, res, next) {

  console.error(err);

  res.status(500).json({
    success: false,
    message: "Internal server error"
  });
}

module.exports = errorHandler;

12 • Production Database

Using a Production Database

A production application should not normally depend on a database running only on the developer's personal computer.

A managed database service such as MongoDB Atlas can provide a hosted MongoDB environment that the deployed application can connect to.

Development

Local MongoDB
mongodb://127.0.0.1:27017/zensus

Production

Environment Variable
MONGODB_URI=mongodb+srv://username:password@cluster.mongodb.net/zensus
Never expose the production connection string Treat database connection strings as credentials. Store them as protected environment variables on the deployment platform.

Production Database Considerations

  • Authentication and access control
  • Backups
  • Connection limits
  • Indexes
  • Monitoring
  • Data recovery
  • Least-privilege database users

14 • Production Security

Production Security Checklist

A working API is not automatically a secure API. Production security requires multiple layers of protection.

Helmet

Helmet helps configure several security-related HTTP headers.

Install
npm install helmet
server.js
const helmet = require("helmet");

app.use(helmet());

Rate Limiting

Rate limiting restricts how frequently clients can make requests. It is particularly useful for authentication and other sensitive endpoints.

Install
npm install express-rate-limit
Rate Limiter
const rateLimit = require("express-rate-limit");

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 10,
  message: {
    message: "Too many login attempts. Try again later."
  }
});

app.use("/api/auth/login", loginLimiter);

CORS

Cross-Origin Resource Sharing controls which browser origins are allowed to make cross-origin requests.

Example
const cors = require("cors");

app.use(cors({
  origin: "https://your-frontend.example"
}));
Production Rule Avoid blindly allowing every origin with permissive CORS configuration. Configure allowed origins according to your application architecture.

HTTPS

HTTPS encrypts communication between the client and server. Production applications should use HTTPS so credentials, tokens, and application data are protected while traveling across the network.

15 • API Versioning

API Versioning

APIs evolve over time. Changing an existing response structure can break older clients.

API versioning allows different versions to coexist while clients migrate.

Example

/api/v1/users Older API
→
/api/v2/users New API
Express Routes
app.use("/api/v1/users", userRoutesV1);

app.use("/api/v2/users", userRoutesV2);
Why Version? Versioning provides a controlled way to introduce breaking changes without immediately breaking existing clients.
16 • Health Checks

Health Check Endpoint

A health-check endpoint gives monitoring systems and deployment infrastructure a simple way to determine whether the application is running.

GET /health
app.get("/health", (req, res) => {

  res.status(200).json({
    status: "ok",
    service: "zensus-api",
    timestamp: new Date().toISOString()
  });

});

Example Response

{ "status": "ok", "service": "zensus-api", "timestamp": "2026-09-20T09:00:00.000Z" }
Why Health Checks Matter If a deployment platform or monitoring system cannot reach the health endpoint, it can detect that the application may be unavailable.
17 • Production Example

Production-Style Express API

The following example combines several concepts from this lesson: environment configuration, Express, security middleware, validation, health checks, error handling, and API routes.

Install Dependencies

Terminal
npm init -y

npm install express dotenv helmet cors

npm install express-rate-limit

server.js

server.js
require("dotenv").config();

const express = require("express");
const helmet = require("helmet");
const cors = require("cors");
const rateLimit = require("express-rate-limit");

const app = express();

const PORT = process.env.PORT || 3000;


/* -------------------------
   Security Middleware
-------------------------- */

app.use(helmet());

app.use(cors({
  origin: process.env.FRONTEND_URL || "http://localhost:5173"
}));


/* -------------------------
   Request Parsing
-------------------------- */

app.use(express.json({
  limit: "1mb"
}));


/* -------------------------
   Rate Limiting
-------------------------- */

const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 100
});

app.use("/api", apiLimiter);


/* -------------------------
   Health Check
-------------------------- */

app.get("/health", (req, res) => {

  res.status(200).json({
    status: "ok",
    service: "zensus-api",
    timestamp: new Date().toISOString()
  });

});


/* -------------------------
   Example API
-------------------------- */

app.get("/api/users", (req, res) => {

  res.status(200).json({
    success: true,
    users: []
  });

});


app.post("/api/users", (req, res) => {

  const { name, email } = req.body;

  if (!name || !email) {

    return res.status(400).json({
      success: false,
      message: "Name and email are required"
    });

  }

  res.status(201).json({
    success: true,
    message: "User created",
    user: {
      name,
      email
    }
  });

});


/* -------------------------
   404 Handler
-------------------------- */

app.use((req, res) => {

  res.status(404).json({
    success: false,
    message: "Route not found"
  });

});


/* -------------------------
   Global Error Handler
-------------------------- */

app.use((err, req, res, next) => {

  console.error(err);

  res.status(500).json({
    success: false,
    message: "Internal server error"
  });

});


/* -------------------------
   Start Server
-------------------------- */

app.listen(PORT, () => {

  console.log(
    `Server running on port ${PORT}`
  );

});

Run the API

Terminal
node server.js
Server running on port 3000

19 • Common Mistakes

Common API Testing & Deployment Mistakes

Production APIs must also be tested with invalid input, missing fields, unauthorized requests, nonexistent resources, duplicate records, and unexpected conditions.

Database passwords, JWT secrets, and API keys should not be hardcoded into source files. Use environment configuration and protected deployment secrets.

If important functionality is tested only manually, regressions can easily be missed after future changes.

A deployed application cannot normally use a database that exists only on your development machine. Configure a production-accessible database.

Stack traces and internal implementation details should not normally be exposed to end users in production.

Deployment is not the end of the process. Applications need logs, health checks, monitoring, alerting, and maintenance.
